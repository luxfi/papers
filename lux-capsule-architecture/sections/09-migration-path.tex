\section{Migration Path}
\label{sec:migration}
% ============================================================================

Existing applications built on Firebase, Supabase, Notion APIs, or similar
centralized backends can migrate to capsule-based architectures incrementally.

\subsection{Migration Strategy}

\begin{enumerate}[nosep]
  \item \textbf{Phase 1: Dual-write.} The application writes to both the
        existing backend and a local capsule vault. Reads come from the
        centralized backend. This validates data model compatibility.
  \item \textbf{Phase 2: Local-read.} Reads switch to the local vault.
        The centralized backend becomes a sync target (write-through).
        The user experiences offline capability and reduced latency.
  \item \textbf{Phase 3: Cut-over.} The centralized backend is removed from
        $\Sigma$. The capsule's CRDT sync handles replication. Identity
        migrates to I-Chain. The old backend is decommissioned.
\end{enumerate}

The key constraint: the application's data model must fit SQLite's relational
schema. Document databases (Firestore, MongoDB) require schema normalization.
Key-value stores map directly. Graph data requires an adjacency-list
representation or a dedicated CRDT type.
