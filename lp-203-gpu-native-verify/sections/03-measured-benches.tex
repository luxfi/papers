\section{Measured Benches: NVIDIA GB10 Grace Blackwell sm\_120}
\label{sec:measured}

\paragraph{Provenance.} All numbers in this section were measured
2026-06-04 on \texttt{spark} (DGX Spark, NVIDIA GB10 Grace
Blackwell Superchip, sm\_120, CUDA 13.0.88, driver 580.159.03,
\SI{121}{GiB} unified memory, 48 SMs)
\cite{blackwell2024,gracehopper2023}. The benchmark source is
\texttt{/tmp/gpu-vtbl-bench/bench.c} calling the public
\texttt{lux\_gpu\_*} C API; the backend is the CUDA
plugin at \texttt{lux-private/gpu-kernels/backends/cuda/}
(\texttt{build-wire/libluxgpu\_backend\_cuda.so}, ABI v12,
sm\_120 native). Each row reports a measurement, not a
projection.

\subsection{BLS12-381 EIP-2537 pairing}

The headline GPU primitive on Blackwell is the BLS12-381
EIP-2537 pairing kernel \cite{eip2537,bls12381}. The Miller loop
plus final exponentiation run on the GPU; multiple pairings batch
into one kernel grid.

\paragraph{Per-pairing crossover.} GPU per-pair
(\SI{19}{\micro\second}) beats single-thread CPU blst
\cite{blst} ($\sim$\SI{1}{\milli\second}) from $N{=}1$; beats
20-core parallel CPU ($\sim$\SI{50}{\micro\second} per pair)
from $N{\geq}3{-}4$. For block-verify workloads ($N{\geq}64$
typical) the GPU is unambiguously the right substrate.

\paragraph{Comparison to the prior projection.} The earlier LP-203
draft projected BLS verify at \SI{0.5}{\micro\second} to
\SI{1.5}{\micro\second} per signature from H100 FP64 plus Miller
loop arithmetic. The measured GB10 cost is
\SI{17.8}{\micro\second} to \SI{19.1}{\micro\second} per pair --
\emph{about} $10\times$ slower than that projection. The driver
is real-Miller-loop overhead measured on sm\_120 silicon, not
roofline arithmetic. Subsequent LPs that depend on per-pair
timing should use the measured number.

per pair on a 20-core part drawing $\sim$\SI{150}{\watt} TDP
deliver $\sim$\num{130} pairings per watt -- two orders of
magnitude worse per watt than GB10.

\paragraph{Per-hash crossover.} GPU baseline at $\sim$\SI{200}{
\micro\second} per kernel launch is launch-overhead-dominated for
single hashes. CPU single-thread keccak runs at
\SI{0.4}{\micro\second} to \SI{0.9}{\micro\second} per op. GPU
wins from $N{\geq}\sim$\num{500} (single-thread CPU comparison)
or $N{\geq}\sim$\num{10000} (20-core parallel CPU comparison).
The kernel is small-input-optimized; large-input single-keccak
(\SI{1}{MiB}) hits only \SI{19}{MB/s} throughput, which is
\emph{not} the intended workload.

\subsection{What the measured numbers say}

Two assertions from the measured set:

\begin{enumerate}[leftmargin=2em,nosep]
\item \textbf{Grace Blackwell's BLS12-381 pairing is
  production-ready.} At \SI{19}{\micro\second} per pair
  sustained, $N{=}256$ batches deliver $\approx$
  \num{49197}~pairings/sec at \SI{20}{\watt}. A 1000-tx block
  of BLS-signed transactions verifies in
  $\sim$\SI{20}{\milli\second} per block on a single GPU.
\item \textbf{Keccak256 is a side-car, not the bottleneck.}
  At \SI{11.38}{\mega\hertz} sustained, hashing 1000 leaves
  costs $<$\SI{1}{\milli\second} -- well below the BLS verify
  cost above. Merkle reduction is bottlenecked by the
  reduction tree's $\log_2(N)$ kernel-launch chain, not the
  per-hash cost.
\end{enumerate}

The next assertion (PQ-strict end-to-end on GPU at
\SI{15}{\milli\second}--\SI{50}{\milli\second}) requires the
composite signature-verify wrappers to land. Until then it is a
projection, not a measurement.
