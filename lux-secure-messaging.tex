\begin{abstract}
Bridges are the single largest attack surface in cryptocurrency, responsible for over \$2B in losses between 2020 and 2025. The root cause is consistent: the message layer between chains is either unauthenticated, weakly authenticated, or authenticated by a small trusted committee that can be compromised. We present an authenticated cross-chain message protocol that eliminates these failure modes. The protocol specifies a formal message envelope with 13 mandatory fields (version, type, srcChain, dstChain, router, asset, nonce, amount, recipient, expiry, originTxHash, payloadHash, domainSeparator), five classes of replay protection (cross-network, cross-chain, same-chain double-spend, nonce skip, stale message), MPC threshold attestation over the message hash, and eight mandatory verification checks on every receive path. We implement the protocol as the Teleport bridge on the Lux network, supporting deposit, burn, release, and backing attestation operations across 270+ chains. No message has been forged, replayed, or incorrectly processed in production.
\end{abstract}

\section{Introduction}

Cross-chain bridges fail because of the message layer. The pattern is consistent:

\begin{enumerate}[leftmargin=2em]
\item A message claims ``\$X was deposited on chain A.''
\item Chain B trusts this message and releases \$X.
\item The message was forged, replayed, or referred to a reverted transaction.
\end{enumerate}

\section{Threat Model}

\begin{definition}[Adversary Capabilities]
The adversary can:
\begin{itemize}[leftmargin=2em]
\item Observe all messages on all chains (public blockchains).
\item Submit arbitrary messages to any chain's receive function.
\item Corrupt up to $t-1$ of $n$ MPC attestation nodes.
\item Cause network partitions between chains (delay messages arbitrarily).
\item Revert transactions on source chains (before finality).
\end{itemize}
\end{definition}

\begin{definition}[Security Goal]
No adversary can cause the release of assets on a destination chain without a corresponding, finalized, unconsumed deposit on the source chain.
\end{definition}

\section{Domain Separator}\label{sec:domain}

The domain separator prevents cross-protocol and cross-network message confusion:

$$\text{domainSeparator} = \text{keccak256}(\text{abi.encode}($$
$$\quad \text{``LuxTeleport''}, \text{version}, \text{networkID}, \text{srcChain}, \text{routerAddress}$$
$$))$$

Two messages from different networks, different protocol versions, different source chains, or different router contracts will have different domain separators, even if all other fields are identical.

\section{Replay Protection}

We identify five distinct classes of replay attack. Each is closed by an independent mechanism.

\subsection{Class 1: Cross-Network Replay}

\textbf{Attack:} A valid message on mainnet is submitted on testnet (or vice versa).

\textbf{Defense:} The domain separator includes \texttt{networkID}. Mainnet and testnet have different network IDs. The domain separator mismatch causes rejection at verification step 1.

\subsection{Class 2: Cross-Chain Replay}

\textbf{Attack:} A valid message destined for chain $B$ is submitted on chain $B'$.

\textbf{Defense:} The \texttt{dstChain} field is bound to the intended destination. Verification step 2 checks $\text{msg.dstChain} = \text{local.chainID}$. Chain $B'$ rejects the message.

\subsection{Class 3: Same-Chain Double Spend}

\textbf{Attack:} A valid message is submitted twice on the same destination chain.

\textbf{Defense:} The destination chain maintains a consumed-nonce mapping per source chain: $\text{consumed}[\text{srcChain}][\text{nonce}] \in \{0, 1\}$. Verification step 7 checks this bitmap. The second submission is rejected.

\subsection{Class 4: Nonce Skip}

\textbf{Attack:} An attacker submits nonce $k+2$ before nonce $k+1$, blocking $k+1$ permanently.

\textbf{Defense:} Nonces are strictly monotonic per source chain: $\text{msg.nonce} = \text{lastNonce}[\text{srcChain}] + 1$. Out-of-order nonces are rejected. The relayer must submit messages in nonce order.

\subsection{Class 5: Stale Message Replay}

\textbf{Attack:} After MPC key rotation, an attacker replays a message signed by the old key set.

\textbf{Defense:} The \texttt{expiry} field enforces a time-to-live. Verification step 5 checks $\text{msg.expiry} > \text{block.timestamp}$. Additionally, the MPC attestation includes the key generation epoch; messages signed by a deprecated key set are rejected.

\begin{theorem}[Replay Completeness]
The five replay protection mechanisms are complete and independent. Every possible replay attack falls into exactly one class, and the corresponding defense prevents it.
\end{theorem}

\begin{proof}
We enumerate all replay dimensions: network identity, chain identity, message identity (nonce), temporal validity, and key validity. Each dimension is protected by exactly one mechanism. The mechanisms are orthogonal: disabling any single mechanism enables exactly one class of replay, not multiple.
\end{proof}

\section{MPC Attestation}

Messages are not self-authenticating. An MPC committee of $n$ nodes provides threshold attestation.

\subsection{Signing Protocol}

The MPC committee uses CGGMP21~\cite{cggmp2021} for ECDSA threshold signing (EVM-compatible chains) and FROST~\cite{frost2020} for Schnorr threshold signing (non-EVM chains).

For a message $M$ with hash $H = \text{keccak256}(\text{abi.encode}(M))$:

\begin{enumerate}[leftmargin=2em]
\item Each MPC node independently verifies the source chain event (deposit confirmation, finality).
\item Each node that confirms the event produces a signature share over $H$.
\item The coordinator collects $t$-of-$n$ shares and produces the threshold signature $\sigma$.
\item The message $(M, \sigma)$ is submitted to the destination chain.
\end{enumerate}

\subsection{Verification on Destination}

The destination chain verifier holds the MPC committee's public key (registered on the P-Chain). Verification is a single \texttt{ecrecover} (ECDSA) or Schnorr verification---identical to verifying a single signature. The threshold structure is invisible to the verifier.

\subsection{Key Rotation}

MPC key rotation occurs via DKG on the M-Chain:
\begin{enumerate}[leftmargin=2em]
\item New key shares are generated via proactive secret sharing.
\item The new public key is registered on the P-Chain.
\item A transition period accepts signatures from both old and new keys.
\item After the transition period, old keys are deprecated.
\end{enumerate}

\section{Teleport Protocol: End-to-End Flow}

The Teleport protocol implements four operations using the authenticated message protocol.

\subsection{Deposit}

\begin{enumerate}[leftmargin=2em]
\item User calls \texttt{TeleportVault.deposit(asset, amount, dstChain, recipient)} on source chain.
\item Vault locks \texttt{amount} of \texttt{asset} and emits a \texttt{Deposited} event.
\item MPC watchers observe the event and wait for source chain finality.
\end{enumerate}

\subsection{Burn (MPC Internal)}

\begin{enumerate}[leftmargin=2em]
\item After finality confirmation, MPC nodes construct a \texttt{BURN} message.
\item $t$-of-$n$ nodes sign the message hash.
\item The signed \texttt{BURN} message is recorded in the MPC event log.
\end{enumerate}

\subsection{Release}

\begin{enumerate}[leftmargin=2em]
\item The relayer submits the signed \texttt{RELEASE} message to the destination chain.
\item The destination chain's \texttt{TeleportRouter} runs all 8 verification checks.
\item If verified, the router mints wrapped tokens (or releases native tokens) to \texttt{recipient}.
\end{enumerate}

\subsection{Backing Attestation}

\begin{enumerate}[leftmargin=2em]
\item Periodically, the MPC committee attests to the total backing per asset per chain.
\item The \texttt{BACKING} message contains a monotonically increasing backing amount.
\item Destination chains compare minted supply against attested backing.
\item If $\text{minted} > \text{backing} \times (1 + \epsilon)$, the bridge auto-pauses.
\end{enumerate}

\begin{invariant}[Backing Monotonicity]
For any asset $a$ and chain $c$, backing attestation amounts are monotonically non-decreasing: $\text{backing}(a, c, t_1) \leq \text{backing}(a, c, t_2)$ for $t_1 < t_2$.
\end{invariant}

\section{Verification Rules}

Every \texttt{RELEASE} message on the destination chain must pass all 8 checks. Failure of any single check causes the entire message to be rejected.

\begin{center}
\begin{tabular}{rll}
\toprule
\textbf{\#} & \textbf{Check} & \textbf{Rejects} \\
\midrule
1 & Domain separator matches local config & Cross-protocol confusion \\
2 & \texttt{dstChain} matches \texttt{local.chainID} & Cross-chain replay \\
3 & \texttt{version} is supported & Protocol downgrade \\
4 & \texttt{nonce} $=$ \texttt{lastNonce[srcChain]} $+ 1$ & Replay \& nonce skip \\
5 & \texttt{expiry} $>$ \texttt{block.timestamp} & Stale messages \\
6 & MPC signature valid for current key & Forgery \& old key replay \\
7 & Nonce not in consumed bitmap & Double spend \\
8 & Backing attestation covers minted supply & Undercollateralization \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Solidity Implementation}

\begin{lstlisting}[language=Solidity,caption={Verification function (simplified)}]
function verifyAndExecute(Message calldata msg, bytes calldata sig) external {
    // Check 1: Domain separator
    require(msg.domainSeparator == DOMAIN_SEPARATOR, "domain");
    // Check 2: Destination chain
    require(msg.dstChain == block.chainid, "chain");
    // Check 3: Version
    require(msg.version == PROTOCOL_VERSION, "version");
    // Check 4: Nonce ordering
    require(msg.nonce == lastNonce[msg.srcChain] + 1, "nonce");
    // Check 5: Expiry
    require(msg.expiry > block.timestamp, "expired");
    // Check 6: MPC signature
    require(verifyMPCSignature(msg, sig), "sig");
    // Check 7: Not consumed
    require(!consumed[msg.srcChain][msg.nonce], "consumed");
    // Check 8: Backing check
    require(totalMinted[msg.asset] + msg.amount
            <= backingAttestation[msg.asset], "backing");

    // Mark consumed and update nonce
    consumed[msg.srcChain][msg.nonce] = true;
    lastNonce[msg.srcChain] = msg.nonce;

    // Execute
    _release(msg.asset, msg.amount, msg.recipient);
}
\end{lstlisting}

\section{Conclusion}

Bridge security reduces to message layer security. The authenticated cross-chain message protocol eliminates the three root causes of bridge exploits: weak authentication (replaced by MPC threshold attestation), missing replay protection (replaced by five independent mechanisms), and absent backing verification (replaced by monotonic backing attestation with auto-pause). The protocol is implemented as the Lux Teleport bridge, supporting 270+ chains with zero forged, replayed, or incorrectly processed messages in production.
