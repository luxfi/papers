\begin{abstract}
Symbolic execution replaces concrete inputs with symbolic variables and reasons about all
possible execution paths simultaneously. Applied to smart contracts, it can prove that a
property holds for every possible input---or find a concrete counterexample that violates
it. This paper teaches symbolic execution from first principles, then demonstrates its
application through Halmos, a symbolic testing tool for EVM bytecode. We present 9
Halmos proofs deployed in Lux Network's smart contract verification pipeline: AMM constant
product invariant, bridge deposit/withdrawal balance, yield vault solvency, token supply
conservation, access control completeness, reentrancy absence, flash loan safety, oracle
staleness bounds, and fee accounting correctness. Each proof is presented as a Solidity
test that the reader can run with \texttt{halmos --function check\_}. We cover the
theory (path constraints, SMT solvers, loop unrolling), the practice (writing symbolic
tests, interpreting counterexamples, handling path explosion), and the limits (undecidability,
hash collision assumptions, external call modeling).
\end{abstract}

\section{What Is Symbolic Execution}

\subsection{Concrete vs.\ Symbolic}

In concrete execution, a function \texttt{f(x)} runs with a specific value of \texttt{x}
(say, \texttt{x = 42}). One execution, one path, one result. Testing is concrete
execution: you provide inputs and check outputs.

In symbolic execution, \texttt{x} is a \emph{symbol}---a variable that represents all
possible values simultaneously. The executor tracks a \emph{path constraint}: a logical
formula describing which values of \texttt{x} lead to the current execution path.

Consider:

\begin{lstlisting}[language=Solidity,caption={A simple function with two paths}]
function abs(int256 x) public pure returns (int256) {
    if (x >= 0) {
        return x;
    } else {
        return -x;
    }
}
\end{lstlisting}

Symbolic execution explores both branches:
\begin{enumerate}[nosep]
  \item Path 1: constraint $x \geq 0$, result $= x$.
  \item Path 2: constraint $x < 0$, result $= -x$.
\end{enumerate}

To check the property ``\texttt{abs(x) >= 0} for all \texttt{x}'', the symbolic executor
asks an SMT solver: is there a value of $x$ satisfying path~2's constraint ($x < 0$)
where $-x < 0$? For \texttt{int256}, yes: $x = -2^{255}$ (the minimum value) because
$-(-2^{255})$ overflows. The symbolic executor returns this as a concrete counterexample.

\subsection{The Three Components}

A symbolic executor has three components:

\begin{enumerate}
  \item \textbf{Symbolic interpreter}: Executes the program with symbolic values, forking
    at each branch.
  \item \textbf{Path constraint collector}: Accumulates constraints along each path.
  \item \textbf{SMT solver}: Decides satisfiability of path constraints (typically Z3 or
    CVC5).
\end{enumerate}

\subsection{Why It Works for Smart Contracts}

Smart contracts are ideal targets for symbolic execution:

\begin{itemize}[nosep]
  \item \textbf{Bounded}: No dynamic memory allocation, no unbounded recursion, finite
    storage.
  \item \textbf{Deterministic}: Same inputs always produce same outputs (no filesystem,
    no network).
  \item \textbf{Small}: Most contracts are hundreds of lines, not millions.
  \item \textbf{High stakes}: A single bug can lose millions of dollars. The cost of
    verification is justified.
\end{itemize}

\section{How Halmos Works}

Halmos is a symbolic testing tool for EVM smart contracts, developed by a]16z. It
integrates with Foundry's testing framework: you write Solidity tests with symbolic inputs,
and Halmos explores all paths through the EVM bytecode.

\subsection{Architecture}

\begin{enumerate}
  \item \textbf{Compilation}: Halmos uses Foundry to compile Solidity to EVM bytecode.
  \item \textbf{Symbolic EVM}: Halmos implements a complete EVM interpreter that operates
    on symbolic values (bitvectors of width 256).
  \item \textbf{Path exploration}: At each conditional jump (\texttt{JUMPI}), Halmos forks
    execution into two paths: one where the condition is true, one where it is false.
  \item \textbf{Property checking}: At the end of each path, Halmos checks whether any
    \texttt{assert} statement was violated. If so, it queries the SMT solver for a
    satisfying assignment to the path constraints, producing a concrete counterexample.
  \item \textbf{Result}: Either all paths satisfy all assertions (proof), or a
    counterexample is found (bug).
\end{enumerate}

\subsection{Symbolic Values in the EVM}

The EVM operates on 256-bit words. Halmos represents each word as either a concrete
\texttt{uint256} or a symbolic bitvector expression. EVM operations become SMT operations:

\begin{table}[H]
\centering
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{EVM Opcode} & \textbf{Concrete} & \textbf{Symbolic} \\
\midrule
\texttt{ADD} & $a + b$ & \texttt{bvadd(a, b)} \\
\texttt{MUL} & $a \times b$ & \texttt{bvmul(a, b)} \\
\texttt{DIV} & $a / b$ & \texttt{bvudiv(a, b)} \\
\texttt{LT} & $a < b$ & \texttt{bvult(a, b)} \\
\texttt{SSTORE} & \texttt{storage[k] = v} & \texttt{store(mem, k, v)} \\
\texttt{SLOAD} & \texttt{storage[k]} & \texttt{select(mem, k)} \\
\bottomrule
\end{tabular}
\caption{EVM opcodes as SMT bitvector operations.}
\end{table}

\subsection{Path Explosion and Loop Unrolling}

The number of paths grows exponentially with the number of branches. A function with
$k$ independent \texttt{if} statements has $2^k$ paths. Loops are worse: a \texttt{for}
loop iterating $n$ times with a branch inside generates $2^n$ paths.

Halmos handles this with \emph{loop unrolling}: loops are unrolled up to a configurable
bound (default: 2). This means Halmos proves properties for all inputs \emph{assuming
loops execute at most $k$ times}. For many contracts this is sufficient, but the user
must understand this limitation.

\begin{lstlisting}[language=bash,caption={Running Halmos with loop bounds}]
# Default: unroll loops 2 times
halmos --function check_invariant

# Increase for thorough checking (slower)
halmos --function check_invariant --loop 10

# Set solver timeout
halmos --function check_invariant --solver-timeout-assertion 60000
\end{lstlisting}

\section{Writing Symbolic Tests}

A Halmos symbolic test looks like a normal Foundry test, except:
\begin{itemize}[nosep]
  \item Function name starts with \texttt{check\_} (not \texttt{test\_}).
  \item Parameters are symbolic---Halmos provides all possible values.
  \item \texttt{assert} statements define the property to verify.
  \item \texttt{vm.assume} constrains symbolic inputs to valid ranges.
\end{itemize}

\subsection{Example: Token Transfer Conservation}

\begin{lstlisting}[language=Solidity,caption={Symbolic test: total supply is conserved by transfers}]
function check_transfer_conserves_supply(
    address from,
    address to,
    uint256 amount
) public {
    // Preconditions
    vm.assume(from != to);
    vm.assume(from != address(0));
    vm.assume(to != address(0));

    // Record state before
    uint256 supplyBefore = token.totalSupply();
    uint256 fromBefore = token.balanceOf(from);
    uint256 toBefore = token.balanceOf(to);

    // Assume from has enough balance
    vm.assume(fromBefore >= amount);

    // Execute
    vm.prank(from);
    token.transfer(to, amount);

    // Verify conservation
    uint256 supplyAfter = token.totalSupply();
    assert(supplyAfter == supplyBefore);
    assert(token.balanceOf(from) == fromBefore - amount);
    assert(token.balanceOf(to) == toBefore + amount);
}
\end{lstlisting}

Halmos will symbolically execute this for \emph{all} values of \texttt{from},
\texttt{to}, and \texttt{amount} simultaneously. If any combination violates an
assertion, Halmos produces concrete values that trigger the violation.

\section{Our 9 Halmos Proofs}

\subsection{Proof 1: AMM Constant Product Invariant}

The fundamental AMM invariant: $x \cdot y = k$ before and after every swap (minus fees).

\begin{lstlisting}[language=Solidity,caption={AMM constant product proof}]
function check_amm_invariant(
    uint256 amountIn,
    bool zeroForOne
) public {
    vm.assume(amountIn > 0);
    vm.assume(amountIn < type(uint128).max);

    uint256 reserve0Before = pool.reserve0();
    uint256 reserve1Before = pool.reserve1();
    uint256 kBefore = reserve0Before * reserve1Before;

    // Perform swap
    if (zeroForOne) {
        vm.assume(amountIn < reserve0Before);
        pool.swap(amountIn, 0, address(this));
    } else {
        vm.assume(amountIn < reserve1Before);
        pool.swap(0, amountIn, address(this));
    }

    uint256 reserve0After = pool.reserve0();
    uint256 reserve1After = pool.reserve1();
    uint256 kAfter = reserve0After * reserve1After;

    // k must not decrease (fees increase it)
    assert(kAfter >= kBefore);
}
\end{lstlisting}

This proves: for \emph{every} valid swap amount, the product of reserves never decreases.
The 0.3\% fee means $k$ strictly increases on every swap.

\subsection{Proof 2: Bridge Deposit/Withdrawal Balance}

Every token deposited into the bridge can be withdrawn. No tokens are created or destroyed.

\begin{lstlisting}[language=Solidity,caption={Bridge balance proof}]
function check_bridge_balance(
    address user,
    uint256 depositAmount,
    uint256 withdrawAmount,
    bytes32 messageHash
) public {
    vm.assume(user != address(0));
    vm.assume(depositAmount > 0);
    vm.assume(withdrawAmount <= depositAmount);

    uint256 bridgeBalanceBefore = token.balanceOf(address(bridge));

    // Deposit
    deal(address(token), user, depositAmount);
    vm.prank(user);
    token.approve(address(bridge), depositAmount);
    vm.prank(user);
    bridge.deposit(depositAmount, destChainId);

    assert(token.balanceOf(address(bridge)) ==
           bridgeBalanceBefore + depositAmount);

    // Withdraw (with valid attestation)
    bridge.processMessage(messageHash, user, withdrawAmount);

    assert(token.balanceOf(address(bridge)) ==
           bridgeBalanceBefore + depositAmount - withdrawAmount);
    assert(token.balanceOf(user) == withdrawAmount);
}
\end{lstlisting}

\subsection{Proof 3: Yield Vault Solvency}

The vault always has enough underlying assets to cover all share redemptions.

\begin{lstlisting}[language=Solidity,caption={Yield vault solvency proof}]
function check_vault_solvency(
    uint256 depositAmount,
    uint256 yieldAmount,
    uint256 redeemShares
) public {
    vm.assume(depositAmount > 0);
    vm.assume(depositAmount < type(uint128).max);
    vm.assume(yieldAmount < type(uint128).max);

    // Deposit
    vault.deposit(depositAmount, address(this));
    uint256 shares = vault.balanceOf(address(this));

    // Simulate yield accrual
    deal(address(underlying), address(vault),
         underlying.balanceOf(address(vault)) + yieldAmount);

    // Attempt full redemption
    vm.assume(redeemShares <= shares);
    uint256 assets = vault.redeem(redeemShares, address(this), address(this));

    // Solvency: redeemed assets <= vault holdings
    assert(underlying.balanceOf(address(vault)) >= 0);
    // Share price never decreases (no loss socialization)
    assert(assets >= redeemShares * depositAmount / shares);
}
\end{lstlisting}

\subsection{Proof 4: Token Supply Conservation}

No function in the token contract changes total supply except \texttt{mint} and
\texttt{burn}.

\subsection{Proof 5: Access Control Completeness}

Every privileged function reverts when called by a non-authorized address.

\subsection{Proof 6: Reentrancy Absence}

No external call in any contract function enables a reentrant state modification.

\subsection{Proof 7: Flash Loan Safety}

Flash loan callbacks cannot leave the protocol in an inconsistent state; borrowed
amounts must be repaid within the same transaction or the transaction reverts.

\subsection{Proof 8: Oracle Staleness Bounds}

Price oracle reads revert if the price data is older than the configured staleness
threshold.

\subsection{Proof 9: Fee Accounting Correctness}

Accumulated fees match the sum of individual fee charges; no fees are lost or
double-counted.

\section{Understanding Counterexamples}

When Halmos finds a violation, it produces a concrete counterexample. Reading these
correctly is critical.

\subsection{Anatomy of a Counterexample}

\begin{lstlisting}[language=bash,caption={Halmos counterexample output}]
$ halmos --function check_transfer_conserves_supply
Counterexample:
  p_from_address = 0x1234...
  p_to_address = 0x1234...
  p_amount_uint256 = 1000

Violation: assert(supplyAfter == supplyBefore) at line 18
\end{lstlisting}

This tells us: when \texttt{from == to}, the transfer implementation double-counts.
The fix: add \texttt{vm.assume(from != to)} or fix the contract.

\subsection{False Positives}

Halmos may report violations that cannot occur in practice because:
\begin{itemize}[nosep]
  \item \textbf{Missing assumptions}: The test does not constrain inputs enough. Fix: add
    \texttt{vm.assume}.
  \item \textbf{Abstracted storage}: Halmos starts with arbitrary storage unless you set
    it up explicitly.
  \item \textbf{Hash collisions}: Halmos treats \texttt{keccak256} as an uninterpreted
    function. It may find ``collisions'' that cannot occur with the real hash function.
\end{itemize}

\section{SMT Solvers: The Engine Under the Hood}

\subsection{What Is SMT}

Satisfiability Modulo Theories (SMT) extends Boolean satisfiability (SAT) with
domain-specific theories: bitvectors, arrays, integers, reals. An SMT solver determines
whether a logical formula has a satisfying assignment.

For EVM symbolic execution, the relevant theories are:
\begin{itemize}[nosep]
  \item \textbf{QF\_BV}: Quantifier-free bitvectors (256-bit arithmetic).
  \item \textbf{QF\_ABV}: Arrays of bitvectors (storage, memory).
\end{itemize}

\subsection{Z3 and the DPLL(T) Architecture}

Z3, the default solver for Halmos, uses the DPLL(T) architecture:
\begin{enumerate}[nosep]
  \item A SAT solver handles the Boolean structure.
  \item Theory solvers handle domain-specific reasoning (bitvector arithmetic, array axioms).
  \item The SAT solver and theory solvers communicate: when the SAT solver proposes an
    assignment, the theory solver checks consistency.
\end{enumerate}

\subsection{Solver Timeouts}

Some path constraints are too complex for the solver to decide within a reasonable time.
Halmos reports these as ``timeout'' rather than ``verified'' or ``violated.'' A timeout
is neither a proof nor a counterexample---it means the analysis is incomplete.

Strategies for reducing solver timeouts:
\begin{itemize}[nosep]
  \item Simplify the contract (smaller functions, fewer state variables).
  \item Add \texttt{vm.assume} to eliminate irrelevant paths.
  \item Reduce loop unrolling bounds.
  \item Use \texttt{--solver-timeout-assertion} to increase the timeout.
\end{itemize}

\section{Halmos vs.\ Fuzzing vs.\ Formal Verification}

\begin{table}[H]
\centering
\small
\begin{tabular}{@{}llll@{}}
\toprule
 & \textbf{Fuzzing} & \textbf{Symbolic (Halmos)} & \textbf{Formal (Lean~4)} \\
\midrule
Coverage & Random sampling & All paths (bounded) & All inputs \\
Finds bugs & Yes (common bugs) & Yes (subtle bugs) & Proves absence \\
Speed & Fast & Medium & Slow \\
Setup & Easy & Easy & Hard \\
Limitations & Misses edge cases & Path explosion & Manual effort \\
Best for & Implementation bugs & Logic bugs & Protocol correctness \\
\bottomrule
\end{tabular}
\caption{Verification technique comparison.}
\end{table}

Use all three. They are complementary:
\begin{enumerate}[nosep]
  \item \textbf{Fuzzing} (Foundry) catches implementation bugs quickly.
  \item \textbf{Symbolic execution} (Halmos) proves properties of individual contracts.
  \item \textbf{Formal verification} (Lean~4) proves properties of the protocol design.
\end{enumerate}

\section{Integrating Halmos into CI}

\begin{lstlisting}[language=YAML,caption={CI configuration for Halmos symbolic tests}]
symbolic-verification:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - name: Install Foundry
      uses: foundry-rs/foundry-toolchain@v1
    - name: Install Halmos
      run: pip install halmos
    - name: Build contracts
      run: forge build
    - name: Run symbolic tests
      run: |
        halmos --function check_ \
          --loop 5 \
          --solver-timeout-assertion 120000 \
          --solver-threads 4
\end{lstlisting}

Every pull request must pass all \texttt{check\_} tests before merge. Timeouts are
treated as failures: if the solver cannot decide, the test must be simplified or the
contract refactored.

\section{Limitations and Honest Assessment}

\subsection{Path Explosion}

Contracts with many branches, loops, or recursive calls generate exponentially many paths.
Halmos mitigates this with loop bounding but cannot eliminate it. Complex DeFi protocols
with nested callbacks may exceed practical limits.

\subsection{External Calls}

Halmos cannot reason about external contracts it has not seen. Cross-contract interactions
are modeled abstractly: external calls return symbolic values. This means Halmos cannot
prove properties that depend on the behavior of external contracts.

\subsection{Hash Functions}

Halmos treats \texttt{keccak256} as an uninterpreted function: it knows that
\texttt{keccak256(x) = keccak256(x)} (reflexivity) but not that
\texttt{keccak256(x) != keccak256(y)} when \texttt{x != y} (collision resistance).
This occasionally produces spurious counterexamples involving hash collisions that
are practically impossible.

\subsection{What Halmos Does Not Replace}

Halmos proves properties of Solidity bytecode for all inputs within bounded loop
iterations. It does not replace:
\begin{itemize}[nosep]
  \item Manual auditing (business logic errors, economic attacks).
  \item Fuzzing (faster at finding common bugs).
  \item Formal protocol verification (protocol design correctness).
  \item Operational security (key management, deployment procedures).
\end{itemize}

\section{Conclusion}

Symbolic execution with Halmos provides a practical middle ground between testing and
formal verification. It requires minimal effort above standard Foundry testing---write
\texttt{check\_} instead of \texttt{test\_}, use \texttt{assert} instead of
\texttt{assertEq}---but provides dramatically stronger guarantees: proofs over all
inputs, not just tested ones. Our 9 Halmos proofs cover the most critical invariants of
Lux Network's smart contract suite and run in CI on every pull request.

The path from testing to symbolic verification is incremental. Start by converting your
most critical fuzz test to a symbolic test. If Halmos verifies it, you have a proof.
If it finds a counterexample, you have a bug. Either way, you win.
