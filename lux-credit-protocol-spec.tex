\begin{abstract}
We present the canonical specification for the Lux Credit Protocol, an omnichain system for collateralized credit issuance, cross-chain transport, and atomic settlement. The protocol issues overcollateralized, in-kind redeemable credit tokens (e.g., LETH backed by ETH) subject to hard loan-to-value constraints, with strategy yield accruing to protocol surplus rather than to credit holders. This document establishes the formal asset taxonomy, canonical message schema, system invariants, solvency state machine, failure behavior, and trust assumptions. It serves as the authoritative reference for auditors, counterparties, and implementors. The protocol decomposes into four auditable subsystems---collateral custody, credit issuance, transport/finality, and surplus allocation---each subject to distinct failure classes and verification requirements.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Cross-chain liquidity systems occupy a contested design space between bridges, lending protocols, and synthetic asset platforms. Each framing carries implicit assumptions about user rights, failure modes, and regulatory posture that, if left undefined, produce semantic leakage: code that compiles and deploys but whose economic and legal meaning drifts across contexts.

The Lux Credit Protocol resolves this by committing to a single, precise classification: it is an \emph{omnichain collateralized credit and settlement protocol}. It is not a bridge. It is not a vault. It is not a stablecoin. It is not a liquid staking token. Each of these labels implies properties the system does not possess or obligations it does not accept.

Under this framing, the protocol comprises exactly four subsystems:

\begin{enumerate}[nosep]
  \item \textbf{Collateral custody.} Vault-based asset custody with strategy deployment and cryptographic backing attestation.
  \item \textbf{Credit issuance.} Minting of overcollateralized, in-kind redeemable credit tokens subject to hard LTV caps.
  \item \textbf{Transport and finality.} Omnichain message relay with per-chain finality thresholds and threshold signature verification.
  \item \textbf{Surplus allocation.} Protocol equity accrual from strategy yield, structurally separated from credit holder claims.
\end{enumerate}

Each subsystem is audited against different failure classes. This decomposition determines which invariants attach to which code paths, which failure modes trigger which recovery procedures, and which guarantees are offered to which participants.

\paragraph{Scope.} This document freezes the protocol semantics. It defines terminology, asset classes, message formats, invariants, the solvency state machine, failure behavior, trust assumptions, and the boundary conditions with the ATS compliance layer. Line-by-line router review proceeds from this specification, not the other way around.


\section{Asset Taxonomy}
\label{sec:taxonomy}

Three mutually exclusive asset classes exist within the protocol. Conflating classes is a protocol violation enforceable at both the contract and legal layers.

\subsection{Class~1: Credit Assets}
\label{sec:credit}

\begin{definition}[Credit Asset]
A credit asset is an overcollateralized, in-kind redeemable liability of the protocol, minted against vault-backed base assets subject to a hard LTV cap.
\end{definition}

\noindent\textbf{Instances.} LETH (backed by ETH), LBTC (backed by BTC).

\begin{requirement}[Credit Asset Properties]
\label{req:credit}
A credit asset \textsc{must} satisfy all of the following:
\begin{enumerate}[nosep]
  \item Minted only against recognized, attested backing.
  \item Redeemable 1:1 in kind: $\texttt{burn}(x) \Rightarrow \texttt{release}(x)$ of the underlying base asset.
  \item Hard issuance cap at or below the configured LTV ratio.
  \item No direct claim on strategy yield.
  \item No governance, profit-share, or security rights.
\end{enumerate}
\end{requirement}

\begin{invariant}[Class Separation]
\label{inv:class-sep}
\[
  \texttt{creditAsset} \neq \texttt{yieldShare} \neq \texttt{securityToken}
\]
Enforced technically and legally via separate token contracts, separate registries, separate accounting buckets, and separate disclosures. A single contract or accounting path \textsc{must not} conflate two classes.
\end{invariant}

\paragraph{Canonical phrasing.} For regulatory filings, disclosures, and counterparty agreements:

\begin{quote}
\emph{LETH is a protocol-issued, fully collateralized, in-kind redeemable credit token backed by ETH vault assets and minted subject to a hard maximum loan-to-value ratio of 90\%, with strategy yield accruing to protocol surplus rather than to LETH holders.}
\end{quote}


\subsection{Class~2: Yield and Equity Instruments}
\label{sec:yield}

\begin{definition}[Yield/Equity Instrument]
A yield/equity instrument represents a claim on protocol surplus, not on redemption principal backing.
\end{definition}

\noindent\textbf{Instances.} xLUX, protocol equity accounting unit.

\begin{requirement}[Yield Instrument Properties]
\label{req:yield}
\begin{enumerate}[nosep]
  \item Absorbs upside from strategy earnings.
  \item May absorb losses after buffer depletion, depending on instrument design.
  \item Never used as collateral equivalence for credit redemptions unless explicitly approved by governance action.
\end{enumerate}
\end{requirement}

The structural separation between credit assets and yield instruments is the primary mechanism by which the protocol avoids characterization as a security or investment contract with respect to credit holders.


\subsection{Class~3: Security Assets}
\label{sec:security}

\begin{definition}[Security Asset]
A security asset is issued and controlled under the ATS/compliance layer and is not fungible with protocol credit liabilities.
\end{definition}

\noindent\textbf{Instances.} Tokenized equity, fund interests, real-world assets.

\begin{requirement}[Security Asset Properties]
\label{req:security}
\begin{enumerate}[nosep]
  \item Compliance-enforced transferability (whitelist, lockup, KYC).
  \item Jurisdictional controls per offering type.
  \item Separate wrapping policy when bridged into Lux (Section~\ref{sec:ats-boundary}).
\end{enumerate}
\end{requirement}


\section{Canonical Bridge Message Schema}
\label{sec:messages}

The message layer is frozen at this specification version. No additional message types may be introduced without a protocol upgrade.

\subsection{Message Types}

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Type} & \textbf{Semantics} \\
\midrule
\texttt{DEPOSIT\_V1}  & Lock base asset; mint credit on destination \\
\texttt{BURN\_V1}     & Burn credit token on source chain \\
\texttt{RELEASE\_V1}  & Release base asset on destination chain \\
\texttt{BACKING\_V1}  & Backing attestation from vault oracle \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Common Envelope}

Every message \textsc{must} include the following 13 fields:

\begin{center}
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Field} & \textbf{Type} & \textbf{Description} \\
\midrule
\texttt{version}         & \texttt{uint8}   & Schema version \\
\texttt{messageType}     & \texttt{uint8}   & Enum (4 types) \\
\texttt{srcChainId}      & \texttt{uint256} & Source chain \\
\texttt{dstChainId}      & \texttt{uint256} & Destination chain \\
\texttt{routerAddress}   & \texttt{address} & Sending router \\
\texttt{assetId}         & \texttt{bytes32} & Canonical asset ID \\
\texttt{nonce}           & \texttt{uint256} & Per-router sequence \\
\texttt{amount}          & \texttt{uint256} & Transfer amount (wei) \\
\texttt{recipient}       & \texttt{bytes32} & Destination address \\
\texttt{expiry}          & \texttt{uint256} & Expiration timestamp \\
\texttt{originTxHash}    & \texttt{bytes32} & Source event hash \\
\texttt{payloadHash}     & \texttt{bytes32} & Typed payload hash \\
\texttt{domainSeparator} & \texttt{bytes32} & Deployment domain \\
\bottomrule
\end{tabular}
\end{center}

The \texttt{domainSeparator} is computed as:
\begin{equation}
\texttt{keccak256}\!\left(\texttt{abi.encode}\!\left(\mathcal{N},\; \mathcal{V},\; c,\; r\right)\right)
\end{equation}
where $\mathcal{N}$ is the protocol name, $\mathcal{V}$ the protocol version, $c$ the chain ID, and $r$ the router address. This closes five replay classes: chain replay, deployment replay, migration replay, same-signature context reuse, and duplicated source event processing.


\subsection{Receive-Path Verification}

\begin{requirement}[Minimum Verification Rules]
\label{req:verify}
Every receive path \textsc{must} verify all of the following before executing any state change:
\begin{enumerate}[nosep]
  \item $\texttt{block.timestamp} \leq \texttt{expiry}$
  \item $\texttt{dstChainId} = \texttt{block.chainid}$
  \item $\texttt{routerAddress} = \texttt{address(this)}$
  \item $\texttt{nonce}$ unused for $(\texttt{srcChainId},\, \texttt{routerAddress},\, \texttt{assetId})$
  \item $\texttt{amount} > 0$
  \item $\texttt{recipient} \neq 0$
  \item $\texttt{assetId}$ recognized and enabled
  \item Message hash signed by $\geq t$ of $n$ authorized signers
\end{enumerate}
\end{requirement}


\section{System Invariants}
\label{sec:invariants}

Let $B$ denote total backing value, $L$ total outstanding credit liabilities, and $E = B - L$ protocol equity. All values are denominated in the base asset's native unit.

\subsection{Core Issuance Invariant}

\begin{invariant}[Issuance Cap]
\label{inv:issuance}
\begin{equation}
  L \leq \lambda \cdot B
\end{equation}
where $\lambda = \texttt{issuanceLtvCap}$. For LETH with $\lambda = 0.9$: $L \leq 0.9 \cdot B$. Checked on every mint; reverts on violation.
\end{invariant}

\subsection{Redemption Invariant}

\begin{invariant}[In-Kind Redemption]
\label{inv:redemption}
\begin{equation}
  \texttt{burn}(x\;\text{LETH}) \Rightarrow \texttt{release}(x\;\text{ETH})
\end{equation}
subject only to finality delay (Section~\ref{sec:finality}), solvency state constraints (Section~\ref{sec:state-machine}), and applicable compliance requirements.
\end{invariant}

\subsection{Parity Invariant}

\begin{invariant}[Unit Parity]
\label{inv:parity}
Redeemable principal per unit of credit token equals exactly one unit of the base asset at all times, independent of surplus level or strategy performance.
\end{invariant}

\subsection{Equity Threshold}

\begin{invariant}[Minimum Equity Ratio]
\label{inv:equity}
Under maximum LTV $\lambda$:
\begin{equation}
  \frac{E}{B} \geq 1 - \lambda \quad\Leftrightarrow\quad \frac{L}{B} \leq \lambda
\end{equation}
For $\lambda = 0.9$: equity ratio $\geq 10\%$, leverage ratio $\leq 90\%$.
\end{invariant}


\section{Solvency State Machine}
\label{sec:state-machine}

The protocol defines exactly four solvency states. All transitions are deterministic given $B$ and $L$. No transition requires operator discretion.

\subsection{States}

\begin{definition}[Healthy]
$B \geq L / \lambda$ and $B \geq L$. All operations permitted.
\end{definition}

\begin{definition}[Restricted Mint]
$B < L / \lambda$ but $B \geq L$. Equity buffer depleted; principal still covered. Mint \textbf{disabled}. Burn and release allowed. Strategy deployment halted; withdrawals initiated.
\end{definition}

\begin{definition}[Emergency]
$B < L$. System undercollateralized on principal basis. Mint \textbf{disabled}. Burn allowed. Release governed by emergency policy. Strategy withdrawals \textbf{forced}. Recovery governance \textbf{active}.
\end{definition}

\begin{definition}[Recovery]
Post-emergency transitional state. Mint disabled until $E/B \geq 1 - \lambda$. Burn and release allowed. Exit requires governance or MPC quorum.
\end{definition}

\subsection{Auto-Pause Trigger}

An accelerated emergency trigger fires when $B < \alpha \cdot L$ with $\alpha = 0.985$. This immediately halts all outbound operations except burns.


\section{Failure Behavior}
\label{sec:failures}

\subsection{MPC Liveness Failure}
\label{sec:mpc-halt}

\begin{requirement}[MPC Halt Policy]
The protocol \textsc{must} select exactly one mode:

\noindent\textbf{Mode~A: MPC-gated releases.} Mint disabled. Release queue accumulates. No liveness guarantee until $\geq t$ signers recover.

\noindent\textbf{Mode~B: User-executable fallback.} After timeout $T$, users self-relay with burn proof from source chain. Recommended for institutional deployments.
\end{requirement}

\subsection{Stale Backing Report}
\label{sec:stale}

\begin{requirement}[Backing Staleness]
Define $\tau_{\max} = \texttt{maxBackingReportAge}[\texttt{assetId}]$. If no valid \texttt{BACKING\_V1} received within $\tau_{\max}$: mint disabled, burn/release allowed against last confirmed backing, emit \texttt{BackingStale} event.
\end{requirement}

\subsection{Strategy Loss Waterfall}

\begin{requirement}[Loss Absorption]
\begin{enumerate}[nosep]
  \item Loss reduces surplus $E$.
  \item $E \leq 0$: Restricted Mint.
  \item $B < L$: Emergency.
  \item New strategy deployments halted until recapitalization.
\end{enumerate}
\end{requirement}

\subsection{Chain Reorg and Finality}
\label{sec:finality}

\begin{requirement}[Per-Chain Finality]
For each chain $c$: $f_c = \texttt{minFinalityConfirmations}[c]$. Mint and release only after $\geq f_c$ confirmations. A single global constant is \textbf{prohibited}.
\end{requirement}

\subsection{Oracle and Valuation Failure}

\begin{requirement}[Oracle Failure]
Freeze mint for affected asset. Allow only like-for-like redemption. Disable cross-asset accounting on stale prices.
\end{requirement}


\section{ATS to Lux Boundary}
\label{sec:ats-boundary}

\begin{requirement}[Wrapping Rule]
A security token may be transported into Lux \textbf{only} through a wrapper whose compliance posture is explicitly declared and enforced at the wrapper level.
\end{requirement}

\noindent\textbf{Model~1: Strict wrapper.} ATS Security $\to$ Restricted Wrapped Security. Whitelist, restrictions, lockups preserved. Recommended.

\noindent\textbf{Model~2: Dual wrapper.} Adds a second composable representation after explicit compliance transformation. Higher flexibility; more legal ambiguity. Deferred.

\section{Trust Assumptions}
\label{sec:trust}

\begin{enumerate}
  \item \textbf{MPC signer set.} At least $t$ of $n$ signers honest and available. Liveness degrades; safety holds unless $\geq n - t + 1$ collude.
  \item \textbf{Vault custody.} Strategy contracts lack unilateral withdrawal authority exceeding configured limits.
  \item \textbf{Backing oracle.} Attestations delivered within $\tau_{\max}$ and reflect true vault state.
  \item \textbf{Chain finality.} Source transactions final after $f_c$ confirmations. Deeper reorgs outside threat model.
  \item \textbf{ATS compliance.} Wrapper contracts enforce transfer restrictions; the protocol layer does not.
\end{enumerate}


\section{Open Questions for Audit}
\label{sec:open}

\begin{enumerate}
  \item \textbf{Stale-backing redemptions.} Do exits remain permissionless during stale backing? \emph{Recommendation:} stop mint, preserve exits.
  \item \textbf{Emergency release policy.} Halt releases, pro-rata, or FIFO queue? \emph{Recommendation:} FIFO queue with governance-controlled cadence.
\end{enumerate}

These are core user-rights definitions, not implementation details.
