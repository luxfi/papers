\section{Why Not Threshold ML-DSA or Threshold FALCON}

\label{app:no-threshold-mldsa}

\subsection{Threshold ML-DSA}

ML-DSA (FIPS 204, formerly CRYSTALS-Dilithium) uses Fiat-Shamir with
Aborts: the signer samples a masking vector $\mathbf{y}$, commits to
$\mathbf{w} = \mathbf{A}\mathbf{y}$, computes challenge $c$, and forms
response $\mathbf{z} = \mathbf{y} + c\mathbf{s}$.  If
$\|\mathbf{z}\|_\infty$ exceeds $\gamma_1 - \beta$, the signer
\emph{aborts} and restarts.

Thresholdizing this is hard for two reasons:

\begin{enumerate}[nosep]
  \item \textbf{Rejection sampling.}  Each party must independently
    decide whether to abort based on their local share of $\mathbf{z}$.
    But the abort decision depends on the \emph{combined}
    $\mathbf{z} = \sum \lambda_i \mathbf{z}_i$.  No party can evaluate
    this without seeing all shares, creating a circular dependency.
    Proposed workarounds (Espitau et al.~\cite{espitau2024}) use
    relaxed rejection bounds that increase signature size and reduce
    security margins.

  \item \textbf{Hint computation.}  ML-DSA verification uses a ``hint''
    vector $\mathbf{h}$ to reconstruct the high-order bits of
    $\mathbf{w} - c\mathbf{s}_2$ without knowing $\mathbf{s}_2$.
    Computing $\mathbf{h}$ in a threshold setting requires either a
    trusted combiner or an additional MPC round, adding complexity and
    latency.
\end{enumerate}

\textbf{NIST status.}  As of FIPS 204 (August 2024), NIST specifies
ML-DSA for single-signer use only.  No threshold variant is
standardized.  The NIST PQC standardization process has not evaluated
threshold extensions.  Using a non-standard threshold construction in
production consensus would introduce unvetted security assumptions.

\textbf{Quasar's alternative.}  Instead of thresholdizing ML-DSA,
Quasar uses ML-DSA as an \emph{individual} signature (each validator
signs independently) and aggregates via Groth16 on Z-Chain.  The
threshold property is provided by Corona on Q-Chain, which was
designed from the ground up as a threshold scheme with a clean 2-round
protocol and formal EUF-CMA proof~\cite{corona}.

\subsection{Threshold FALCON}

FALCON~\cite{falcon-spec} uses NTRU lattices and a hash-then-sign
paradigm with Gaussian sampling via a Gram-Schmidt-like procedure
(the ``FALCON tree'').  Thresholdizing FALCON requires distributed
Gaussian sampling, which is an open problem:

\begin{enumerate}[nosep]
  \item The FALCON signing key is a short basis for an NTRU lattice.
    Shamir-sharing this basis and reconstructing Gaussian samples from
    shares requires parties to jointly sample from a lattice Gaussian
    without leaking the basis---strictly harder than threshold
    Fiat-Shamir with Aborts.

  \item Known approaches (Ducas and Prest~\cite{ducas2016}) for
    distributed NTRU sampling require $O(n^2)$ communication rounds,
    negating FALCON's performance advantage over ML-DSA.

  \item FALCON was not selected as NIST's primary standard (ML-DSA
    was); it is a secondary standard under FIPS~206 (draft).  Building
    threshold cryptography on a secondary standard adds adoption risk.
\end{enumerate}

\textbf{Quasar's position.}  Neither threshold ML-DSA nor threshold
FALCON are used.  Corona fills the threshold PQ niche.  Individual
ML-DSA signatures provide non-threshold PQ identity binding, aggregated
by Z-Chain into constant-size Groth16 proofs.
