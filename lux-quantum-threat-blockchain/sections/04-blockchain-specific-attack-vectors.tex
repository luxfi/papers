\section{Blockchain-Specific Attack Vectors}

\label{sec:attack-vectors}

\subsection{Attack 1: Mempool Key Exposure}

When a user broadcasts a transaction, the transaction includes a signature from which
the public key can be recovered (ECDSA recovery) or is explicitly included. Between
broadcast and confirmation (typically 2--30 seconds on modern chains), the public key
is visible in the mempool. A quantum adversary monitoring the mempool can:

\begin{enumerate}[leftmargin=2em]
  \item Observe the public key in the pending transaction.
  \item Compute the private key via Shor's algorithm.
  \item Broadcast a competing transaction draining the account with higher gas.
  \item The competing transaction confirms first (front-running).
\end{enumerate}

This attack requires completing Shor's algorithm within the block time. Current
estimates suggest this is infeasible with near-term quantum computers (hours per key
recovery), but may become feasible as quantum hardware improves.

\textbf{Mitigation}: Commit-reveal transaction schemes, where the transaction is
committed (hash only) before revealing the public key. However, this doubles latency
and is not backward compatible with existing EVM transaction formats.

\textbf{Better mitigation}: Post-quantum signatures. If the signature scheme is
quantum-resistant, public key exposure in the mempool is not a threat.

\subsection{Attack 2: Validator Signature Forgery}

Validator BLS keys are published in the validator set and remain static for the
validator's entire stake duration. A quantum adversary can:

\begin{enumerate}[leftmargin=2em]
  \item Recover any validator's BLS private key from their published public key.
  \item Forge signatures for arbitrary blocks, including blocks that conflict with
        the canonical chain.
  \item Create a forged finality certificate (aggregate signature) for a conflicting
        chain, violating the safety property of the consensus protocol.
\end{enumerate}

This is the most severe quantum attack on proof-of-stake blockchains: it breaks
\emph{finality}, the property that confirmed transactions cannot be reversed.

\subsection{Attack 3: Retroactive Chain Compromise}

The permanent, public nature of blockchain data enables retroactive attacks:

\begin{enumerate}[leftmargin=2em]
  \item A quantum adversary recovers private keys from historical public keys
        recorded on-chain.
  \item Transfers all assets from accounts that have ever had their public key
        exposed (any account that has sent a transaction).
  \item For UTXO chains: any output sent to a P2PKH address (public key hash) is
        safe until spent, but any output sent to a P2PK address (raw public key) is
        immediately vulnerable.
\end{enumerate}

For account-based chains (Ethereum, Lux C-Chain), every account that has sent at
least one transaction has its public key permanently recorded on-chain.

\subsection{Attack 4: Cross-Chain Bridge Key Extraction}

Cross-chain bridges typically use MPC (multi-party computation) with ECDSA threshold
signatures. The bridge's public key is on-chain. If the threshold scheme uses a
$(t, n)$ configuration and the adversary can recover any $t$ individual signer public
keys, the adversary can recover each signer's private key independently and forge
bridge signatures.

This is particularly dangerous because bridge contracts typically hold large asset
pools: Wormhole (\$2.4B TVL), LayerZero (\$1.8B TVL), and similar systems are
single-point-of-failure targets.

\subsection{Attack 5: Oracle Attestation Forgery}

Price oracles sign attestations with ECDSA or EdDSA keys. A quantum adversary who
recovers oracle signing keys can forge arbitrary price feeds, enabling:

\begin{itemize}[leftmargin=2em]
  \item Manipulation of DeFi lending protocol liquidations
  \item Artificial arbitrage through forged price discrepancies
  \item Triggering of options/derivatives at manipulated strike prices
\end{itemize}
