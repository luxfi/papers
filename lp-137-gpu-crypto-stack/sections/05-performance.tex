\subsection{Methodology}

\paragraph{CPU baseline.} Single-thread, no SIMD assist beyond what the compiler emits at \texttt{-O3 -march=native}. We deliberately do not multi-thread the CPU baseline; the GPU number is host-thread-counted (one CPU thread dispatches the GPU batch and waits). Multi-threading both sides changes the question to ``how many cores can you afford'' rather than ``what is the substrate's intrinsic GPU acceleration''; we keep it apples-to-apples.

\paragraph{GPU timing.} We measure end-to-end including the input upload, kernel dispatch, and result download. Pinned memory + DMA reduce the host-to-GPU transfer to a fixed cost that amortizes over batch size. The crossover (GPU faster than CPU) is reported per algorithm in LP-137 \texttt{\#crossover}; it is typically between $N=64$ and $N=512$ inputs.

\paragraph{Reproducibility.} Every number in Table~\ref{tab:performance} can be reproduced by:

\begin{lstlisting}[language=bash]
cd lux/crypto/bench
go test -bench=BenchmarkBLSAggregateVerify_Metal/N=1024 -count=10
\end{lstlisting}

\subsection{Acceleration kernels (LP-160 through LP-166)}

Where the headline ratio depends on a fused or batched kernel, the kernel's own LP carries the per-platform breakdown:

\begin{itemize}
\item \textbf{Batched Montgomery inversion} (LP-160 \cite{lp160}): 10--20$\times$ over $N$ Fermat exponentiations at $N=1024$ on Apple M1 Max; consumed by every curve in the corpus.
\item \textbf{Multi-curve Pippenger MSM} (LP-161 \cite{lp161}): one parameterized kernel for secp256k1, BN254, BLS12-381 G1/G2, Banderwagon. Headline win is code consolidation (3{,}200 LOC $\rightarrow{}$ $\sim$600 LOC + per-curve traits).
\item \textbf{Combined-pair Miller loop} (LP-162 \cite{lp162}): 9.5$\times$ on Apple M1 Max for $k=1024$ BLS12-381 batch pairing verify.
\item \textbf{Karatsuba modexp} (LP-163 \cite{lp163}): EIP-198 hot path ($M_{\text{len}} \le 256$) unaffected; Karatsuba kicks in at $M_{\text{len}} \ge 512$ and dominates at $M_{\text{len}} = 4096$.
\item \textbf{Six-step NTT} (LP-164 \cite{lp164}): lifts the radix-2 Cooley-Tukey ceiling past $N = 2^{16}$; the 16.92$\times$ Metal NTT row in Table~\ref{tab:performance} reproduces from this kernel.
\item \textbf{Pedersen tree-reduce} (LP-165 \cite{lp165}): width-256 Verkle vector commit; on Apple M2 Ultra the threadgroup-memory ceiling caps it at 0.73$\times$ vs the legacy two-stage path; on NVIDIA A100/H100 (192 KiB shared/SM) the tree-reduce wins.
\item \textbf{Threshold pre-sign batch} (LP-166 \cite{lp166}): single-pass FROST + CGGMP21 round-1; projected 5.0--7.2$\times$ at $M=7$, $N=64$ vs MPCVM v0.62 sequential.
\end{itemize}

\subsection{Application: the GPU CLOB matcher}
\label{sec:clob-matcher}

The byte-equality methodology of this paper is not specific to
cryptography. The Lux DEX central-limit-order-book (CLOB) matcher is a
non-cryptographic kernel built under the identical contract: a
first-party CPU matcher is the canonical oracle, and each GPU backend is
required to produce byte-identical fill sets on every input. We summarize
it here because it is the highest-throughput consumer of the substrate
and exercises the byte-equality harness on a consensus-critical,
non-crypto workload; the full matcher is specified in the Lux Lightspeed
DEX paper \cite{luxlightspeeddex}.

\paragraph{Per-book arena.} Each order book is a contiguous
device-resident arena (price-level array, resting-order queues, working
fill buffer) matched in place; distinct markets are distinct arenas
matched independently.

\paragraph{Knuth Algorithm-D division.} The throughput-critical inner
operation is the VWAP wide-integer division. Replacing a 512-iteration
bit-serial divide with Knuth's Algorithm~D (multi-word long division,
\emph{TAOCP} Vol.~2 \cite{knuthtaocp2}) gives a measured $\sim$8$\times$
speedup of the matcher kernel --- the single largest lever, and the
reason per-fill latency reaches the single-digit-nanosecond range.

\paragraph{Byte-parity gate.} The GPU matcher must produce byte-identical
fills (same fills, quantities, trade IDs, ordering) as the CPU oracle.
Enforced by millions of randomized fuzz orders plus a KAT corpus, with
zero parity failures. A one-byte divergence fails the gate; matching is
consensus-critical, so the GPU path ships only on exact agreement.

\subsection{What we do not benchmark}

\paragraph{Throughput vs latency.} The numbers above are throughput. For a single signature verify (\texttt{N=1}), CPU is always faster than any GPU; the correct dispatch is to skip the GPU. We do not report ``$1\times$ verify on GPU is X microseconds'' because nobody dispatches that pattern.

\paragraph{Multi-GPU.} The Lux substrate is designed to fan out across multiple GPUs, but the headline numbers are single-GPU (M2 Ultra has one Metal device). Multi-GPU numbers will be reported in a future LP-137 revision once the cluster topology stabilizes.

\paragraph{TFHE end-to-end.} The TFHE numbers in this paper are for the underlying lattice arithmetic (NTT, poly\_mul). End-to-end TFHE program performance (encrypt$\rightarrow$evaluate$\rightarrow$decrypt with bootstrapping) is reported separately in LP-013.
