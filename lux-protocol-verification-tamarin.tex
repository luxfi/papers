\begin{abstract}
Tamarin Prover is a tool for the symbolic analysis of security protocols. It can prove
that a protocol satisfies security properties (authentication, secrecy, forward secrecy)
for \emph{all} possible adversary strategies, not just those a tester thought to try.
This paper teaches Tamarin from first principles: the Dolev-Yao adversary model,
multiset rewriting rules, lemma specification, and proof strategies. We then present
Tamarin models of two Lux Network protocols: the MPC bridge signing protocol (FROST-BLS
threshold signatures over a network adversary) and the hybrid post-quantum TLS handshake
(combining ML-KEM with X25519 for quantum resistance). For each, we verify authentication,
secrecy, and agreement properties, and we show how Tamarin's attack finding mode uncovered
a reflection attack in an early version of the MPC protocol. The reader will learn to
model protocols, specify security properties, run Tamarin, and interpret its output.
\end{abstract}

\section{What Is Protocol Verification}

\subsection{The Problem}

Cryptographic primitives (AES, SHA-256, ECDSA) are well-studied and presumed secure.
But combining secure primitives into a protocol does not automatically produce a secure
protocol. The protocol's \emph{message flow}---who sends what to whom, in what order,
with what checks---introduces new attack surfaces: replay attacks, man-in-the-middle,
reflection attacks, interleaving attacks.

These attacks exploit the protocol logic, not the cryptography. They are extremely hard
to find by code review or testing because they require reasoning about all possible
adversary behaviors, not just one.

\subsection{The Dolev-Yao Model}

Tamarin works in the \emph{Dolev-Yao} adversary model:
\begin{itemize}[nosep]
  \item The adversary controls the network completely: it can intercept, delay, replay,
    and modify any message.
  \item The adversary can perform any cryptographic operation on values it knows (encrypt,
    decrypt with known keys, hash, sign with known keys).
  \item The adversary \emph{cannot} break cryptographic primitives: it cannot decrypt
    without the key, it cannot forge signatures without the private key, it cannot
    invert hash functions.
\end{itemize}

This is a ``perfect cryptography'' model. It separates protocol logic bugs from
cryptographic implementation bugs, allowing each to be analyzed independently.

\subsection{What Tamarin Proves}

Given a protocol model and a security property, Tamarin either:
\begin{enumerate}[nosep]
  \item \textbf{Proves} the property holds for all possible adversary strategies and all
    numbers of protocol sessions (unbounded verification).
  \item \textbf{Finds an attack}: a concrete sequence of adversary actions that violates
    the property.
  \item \textbf{Does not terminate}: the search space is infinite, and Tamarin's heuristics
    fail to converge (rare in practice, common in theory).
\end{enumerate}

\section{Tamarin Fundamentals}

\subsection{Multiset Rewriting Rules}

Tamarin models protocols as sets of \emph{multiset rewriting rules}. Each rule has:
\begin{itemize}[nosep]
  \item \textbf{Premises}: facts that must exist (consumed from the state).
  \item \textbf{Actions}: labels recorded in the trace (for specifying properties).
  \item \textbf{Conclusions}: facts produced (added to the state).
\end{itemize}

\begin{lstlisting}[language=Tamarin,caption={A multiset rewriting rule}]
rule Generate_Key:
    [ Fr(~sk) ]             // Premise: fresh random value
    --[ Generated(~sk) ]->  // Action: record in trace
    [ !SecretKey($A, ~sk),  // Conclusion: persistent fact
      Out(pk(~sk)) ]        // Conclusion: adversary learns public key
\end{lstlisting}

\begin{itemize}[nosep]
  \item \texttt{Fr(\~{}sk)}: a fresh (random) value. The \texttt{\~{}} prefix means ``fresh.''
  \item \texttt{\$A}: a public name (adversary knows it). The \texttt{\$} prefix means ``public.''
  \item \texttt{!SecretKey}: a persistent fact (can be consumed multiple times).
  \item \texttt{Out(pk(\~{}sk))}: sends \texttt{pk(\~{}sk)} to the network (adversary).
\end{itemize}

\subsection{Built-in Cryptographic Functions}

Tamarin provides built-in support for common cryptographic operations:

\begin{lstlisting}[language=Tamarin,caption={Tamarin builtins}]
theory MyProtocol
begin

builtins: hashing, signing, asymmetric-encryption,
          diffie-hellman, symmetric-encryption

// hashing: h(x) -- one-way function
// signing: sign(m, sk), verify(sign(m, sk), m, pk(sk)) = true
// asymmetric-encryption: aenc(m, pk(sk)), adec(aenc(m, pk(sk)), sk) = m
// diffie-hellman: g^x, (g^x)^y = (g^y)^x
// symmetric-encryption: senc(m, k), sdec(senc(m, k), k) = m

end
\end{lstlisting}

\subsection{Specifying Security Properties}

Properties are specified as \emph{lemmas} in first-order temporal logic over the trace:

\begin{lstlisting}[language=Tamarin,caption={Security property specification}]
// Secrecy: the adversary never learns the session key
lemma session_key_secrecy:
  "All A B k #i.
    SessionKey(A, B, k) @i
    ==> not (Ex #j. K(k) @j)"

// Authentication: if B thinks it talked to A,
// then A actually ran the protocol
lemma authentication:
  "All A B k #i.
    Commit(B, A, k) @i
    ==> (Ex #j. Running(A, B, k) @j & j < i)"

// Injective agreement: one-to-one correspondence
lemma injective_agreement:
  "All A B k #i.
    Commit(B, A, k) @i
    ==> (Ex #j. Running(A, B, k) @j & j < i
         & not (Ex B2 #i2. Commit(B2, A, k) @i2 & not (#i = #i2)))"
\end{lstlisting}

\begin{itemize}[nosep]
  \item \texttt{@i} binds a timepoint to the trace.
  \item \texttt{K(k)} means the adversary knows \texttt{k}.
  \item \texttt{Commit} and \texttt{Running} are action labels placed in protocol rules.
  \item \texttt{j < i} means timepoint \texttt{j} occurs before \texttt{i}.
\end{itemize}

\section{Modeling the MPC Bridge Protocol}

Lux Network's Teleport bridge uses FROST-BLS threshold signatures: $t$-of-$n$ validators
collaboratively sign cross-chain messages without any single validator holding the full
private key. The Tamarin model verifies that this protocol is secure against a network
adversary who controls up to $t - 1$ validators.

\subsection{Protocol Description}

The FROST-BLS protocol has three phases:
\begin{enumerate}
  \item \textbf{Key Generation}: Each validator $i$ generates a secret share $s_i$ via
    Feldman's Verifiable Secret Sharing (VSS). The group public key $PK$ is derived from
    the commitments.
  \item \textbf{Signing Round 1}: Each signer $i$ generates a nonce pair $(d_i, e_i)$
    and broadcasts the corresponding commitments $(D_i, E_i)$.
  \item \textbf{Signing Round 2}: Each signer $i$ computes a partial signature
    $z_i = d_i + e_i \cdot \rho_i + \lambda_i \cdot s_i \cdot c$ where $c$ is the
    challenge and $\lambda_i$ is the Lagrange coefficient. Partial signatures are
    aggregated into the group signature $\sigma$.
\end{enumerate}

\subsection{Tamarin Model}

\begin{lstlisting}[language=Tamarin,caption={FROST-BLS key generation in Tamarin}]
theory FROST_BLS
begin

builtins: signing, hashing, multiset

functions: pk/1, lagrange/2, commit/1, verify_share/3,
           aggregate/1 [private]

// Key generation: each validator gets a secret share
rule KeyGen:
    [ Fr(~share_i) ]
    --[ ShareGenerated($V, ~share_i) ]->
    [ !Share($V, ~share_i),
      Out(commit(~share_i)) ]  // VSS commitment is public

// Signing round 1: generate nonces
rule Sign_Round1:
    [ !Share($V, share_i), Fr(~d_i), Fr(~e_i) ]
    --[ Nonce($V, ~d_i, ~e_i) ]->
    [ SignerState1($V, share_i, ~d_i, ~e_i),
      Out(<commit(~d_i), commit(~e_i)>) ]

// Signing round 2: compute partial signature
rule Sign_Round2:
    let z_i = ~d_i + ~e_i * rho + lagrange($V, signers) * share_i * c
    in
    [ SignerState1($V, share_i, ~d_i, ~e_i),
      In(<msg, c, rho, signers>) ]
    --[ PartialSig($V, msg, z_i),
        Running($V, 'Bridge', <msg, z_i>) ]->
    [ Out(z_i) ]

// Aggregation: combine partial signatures
rule Aggregate:
    [ In(<z_1, z_2, z_3>),  // t partial sigs
      In(msg) ]
    --[ Commit('Bridge', 'Validators', <msg, aggregate(<z_1, z_2, z_3>)>),
        Signed(msg, aggregate(<z_1, z_2, z_3>)) ]->
    [ Out(<msg, aggregate(<z_1, z_2, z_3>)>) ]
\end{lstlisting}

\subsection{Security Properties}

\begin{lstlisting}[language=Tamarin,caption={FROST-BLS security properties}]
// Unforgeability: adversary cannot produce a valid signature
// without controlling t shares
lemma unforgeability:
  "All msg sig #i.
    Signed(msg, sig) @i
    ==> (Ex V1 V2 V3 #j1 #j2 #j3.
          PartialSig(V1, msg, _) @j1
        & PartialSig(V2, msg, _) @j2
        & PartialSig(V3, msg, _) @j3
        & not (V1 = V2) & not (V2 = V3) & not (V1 = V3))"

// Nonce secrecy: adversary never learns honest nonces
lemma nonce_secrecy:
  "All V d e #i.
    Nonce(V, d, e) @i & not (Ex #c. Corrupt(V) @c)
    ==> not (Ex #j. K(d) @j) & not (Ex #k. K(e) @k)"

// No nonce reuse: each nonce pair is used exactly once
lemma no_nonce_reuse:
  "All V d e #i #j.
    Nonce(V, d, e) @i & Nonce(V, d, e) @j
    ==> #i = #j"
\end{lstlisting}

\subsection{The Reflection Attack}

During verification of an early protocol version, Tamarin found a reflection attack: if
the protocol did not bind the signer's identity into the nonce commitment, an adversary
could replay validator~A's round-1 message as if it came from validator~B. The adversary
does not learn any secret, but it causes the aggregated signature to be computed with
incorrect Lagrange coefficients, producing an invalid group signature. This is a liveness
attack, not a safety attack, but it causes the bridge to stall.

The fix: bind the signer identity $V$ into the nonce commitment: $D_i = g^{d_i} \cdot H(V \| \text{msg})$.
After this fix, Tamarin proves all properties hold.

\section{Modeling the Hybrid PQ Handshake}

Lux Network uses a hybrid post-quantum TLS handshake that combines X25519 (classical
Diffie-Hellman) with ML-KEM-768 (post-quantum key encapsulation). The hybrid design
ensures security even if one scheme is broken.

\subsection{Protocol Flow}

\begin{enumerate}
  \item \textbf{ClientHello}: Client sends $g^x$ (X25519 ephemeral) and $\mathsf{ek}$
    (ML-KEM encapsulation key).
  \item \textbf{ServerHello}: Server computes $g^y$ (X25519 ephemeral), encapsulates
    $(\mathsf{ct}, K_{\text{pq}}) \leftarrow \mathsf{Encaps}(\mathsf{ek})$, and derives
    the session key: $K = \mathsf{KDF}(g^{xy} \| K_{\text{pq}})$.
  \item \textbf{Finished}: Both sides confirm the session key via MAC.
\end{enumerate}

\subsection{Tamarin Model}

\begin{lstlisting}[language=Tamarin,caption={Hybrid handshake in Tamarin}]
theory HybridHandshake
begin

builtins: diffie-hellman, hashing, symmetric-encryption

functions: encaps/2, decaps/2, mlkem_pk/1,
           kdf/1

equations: decaps(encaps(k, mlkem_pk(sk)), sk) = k

// Client Hello
rule Client_Hello:
    [ Fr(~x), Fr(~ek_seed) ]
    --[ ClientInit($C, $S, ~x) ]->
    [ ClientState($C, $S, ~x, ~ek_seed),
      Out(<'ClientHello', 'g'^~x, mlkem_pk(~ek_seed)>) ]

// Server Hello
rule Server_Hello:
    [ In(<'ClientHello', gx, ek>),
      Fr(~y), Fr(~k_pq) ]
    --[ let ss = kdf(<gx^~y, ~k_pq>) in
        ServerSession($S, $C, ss),
        Running($S, $C, ss) ]->
    [ ServerState($S, $C, ~y, ~k_pq, kdf(<gx^~y, ~k_pq>)),
      Out(<'ServerHello', 'g'^~y, encaps(~k_pq, ek),
           senc('server_finished', kdf(<gx^~y, ~k_pq>))>) ]

// Client Finished
rule Client_Finished:
    [ ClientState($C, $S, ~x, ~ek_seed),
      In(<'ServerHello', gy, ct, server_fin>) ]
    --[ let k_pq = decaps(ct, ~ek_seed) in
        let ss = kdf(<gy^~x, k_pq>) in
        Eq(server_fin, senc('server_finished', ss)),
        ClientSession($C, $S, ss),
        Commit($C, $S, ss) ]->
    [ Out(senc('client_finished', ss)) ]

// Equality check
restriction Equality:
  "All x y #i. Eq(x, y) @i ==> x = y"
\end{lstlisting}

\subsection{Properties Verified}

\begin{lstlisting}[language=Tamarin,caption={Hybrid handshake security properties}]
// Session key secrecy under Dolev-Yao
lemma session_secrecy:
  "All C S k #i.
    ClientSession(C, S, k) @i
    & not (Ex #c. Corrupt(C) @c)
    & not (Ex #c. Corrupt(S) @c)
    ==> not (Ex #j. K(k) @j)"

// Forward secrecy: even if long-term keys are later compromised,
// past session keys remain secret
lemma forward_secrecy:
  "All C S k #i #c1 #c2.
    ClientSession(C, S, k) @i
    & Corrupt(C) @c1 & Corrupt(S) @c2
    & i < c1 & i < c2
    ==> not (Ex #j. K(k) @j)"

// Hybrid security: session key is secure if EITHER
// DH or ML-KEM is secure (not both need to hold)
lemma hybrid_security:
  "All C S k #i.
    ClientSession(C, S, k) @i
    & not (Ex #c. Corrupt(C) @c)
    & not (Ex #c. Corrupt(S) @c)
    ==> not (Ex #j. K(k) @j)"
\end{lstlisting}

\subsection{Installation}

brew install tamarin-prover

git clone https://github.com/tamarin-prover/tamarin-prover.git

\subsection{Running Proofs}

\begin{lstlisting}[language=bash,caption={Running Tamarin}]
# Prove all lemmas
tamarin-prover --prove FROST_BLS.spthy

# Interactive mode (web UI for exploring proof trees)
tamarin-prover interactive FROST_BLS.spthy
# Then open http://localhost:3001 in a browser

# Prove specific lemma
tamarin-prover --prove=unforgeability FROST_BLS.spthy
\end{lstlisting}

\subsection{Interpreting Output}

Tamarin outputs one of three results for each lemma:
\begin{itemize}[nosep]
  \item \texttt{verified}: The property holds for all possible adversary strategies.
  \item \texttt{falsified}: An attack was found. Tamarin outputs the attack trace.
  \item \texttt{analysis incomplete}: Tamarin could not determine the result (may require
    manual guidance via proof oracles or lemma ordering).
\end{itemize}

\section{Common Pitfalls}

\subsection{Forgetting to Model the Adversary}

If you do not explicitly model what the adversary can learn (via \texttt{Out} facts),
Tamarin assumes the adversary learns nothing. This makes proofs trivially true and
useless. Always output public values and consider what the adversary observes.

\subsection{Unbounded Sessions}

Tamarin verifies properties for an unbounded number of sessions. But this means the
state space is infinite. If Tamarin does not terminate, try adding \emph{sources lemmas}:
helper lemmas that constrain where certain facts can originate.

\subsection{Equational Theories}

Custom equational theories (e.g., for lattice-based cryptography) can make Tamarin's
unification procedure non-terminating. Stick to built-in theories when possible. For
post-quantum primitives, model them as uninterpreted functions with explicit
\texttt{equations} for the decapsulation property.

\section{Tamarin vs.\ ProVerif}

ProVerif is another automated protocol verifier. Key differences:

\begin{table}[H]
\centering
\small
\begin{tabular}{@{}lll@{}}
\toprule
 & \textbf{Tamarin} & \textbf{ProVerif} \\
\midrule
State & Stateful (multiset rewriting) & Stateless (Horn clauses) \\
Sessions & Exact, unbounded & Over-approximation \\
False positives & None & Possible \\
Automation & Semi-automatic & Fully automatic \\
Speed & Slower & Faster \\
Expressiveness & Higher & Lower \\
\bottomrule
\end{tabular}
\caption{Tamarin vs.\ ProVerif comparison.}
\end{table}

Use ProVerif for a quick first check. Use Tamarin for the definitive proof, especially
for stateful protocols like MPC signing where session state matters.

\section{Conclusion}

Protocol bugs are the hardest bugs to find and the most expensive to exploit. Tamarin
Prover provides machine-checked guarantees that a protocol is secure against all
adversary strategies in the Dolev-Yao model. For Lux Network, Tamarin verification of
the FROST-BLS bridge protocol found a reflection attack that would have caused bridge
liveness failures, and verified that the hybrid PQ handshake provides forward secrecy
even against quantum-capable adversaries.

The investment is modest: each protocol model took 2--3 days to write and seconds to
verify. The return is certainty that the protocol logic is correct, independent of the
implementation.
