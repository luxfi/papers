\begin{abstract}
We present an implementation of Hybrid Public Key Encryption (HPKE) as defined in RFC 9180 as an EVM precompile for the Lux blockchain. HPKE combines the security of asymmetric key encapsulation with the efficiency of symmetric authenticated encryption, providing a standardized framework for public key encryption. Our precompile supports multiple cipher suites including P-256, P-384, P-521, and X25519 key encapsulation mechanisms paired with HKDF key derivation and AES-GCM or ChaCha20-Poly1305 authenticated encryption. We detail the protocol integration, security properties, gas cost analysis, and applications including encrypted messaging, sealed-bid auctions, and confidential smart contract inputs.
\end{abstract}

\section{Introduction}

Public key encryption enables secure communication between parties without pre-shared secrets. However, direct public key encryption (e.g., ElGamal, RSA-OAEP) is inefficient for variable-length messages. Hybrid encryption addresses this by using public key cryptography only for key encapsulation, then encrypting the actual message with efficient symmetric algorithms.

IETF RFC 9180 standardizes Hybrid Public Key Encryption (HPKE), providing:

\begin{itemize}
\item \textbf{Key Encapsulation}: Secure key agreement using elliptic curves
\item \textbf{Key Derivation}: HKDF-based key derivation with context binding
\item \textbf{Authenticated Encryption}: AEAD for confidentiality and integrity
\item \textbf{Multiple Modes}: Base, PSK, Auth, and AuthPSK modes
\end{itemize}

On-chain HPKE enables new privacy-preserving applications: encrypted messages in smart contracts, sealed-bid auctions, confidential transaction data, and secure key management.

\section{HPKE Protocol}

\subsection{Components}

HPKE consists of three components:

\begin{definition}[Key Encapsulation Mechanism (KEM)]
A KEM provides:
\begin{itemize}
\item $\text{Encap}(pk_R) \to (k, \text{enc})$: Generate shared secret $k$ and encapsulation $\text{enc}$
\item $\text{Decap}(\text{enc}, sk_R) \to k$: Recover shared secret from encapsulation
\end{itemize}
\end{definition}

\begin{definition}[Key Derivation Function (KDF)]
A KDF expands keying material:
\begin{itemize}
\item $\text{Extract}(\text{salt}, \text{ikm}) \to \text{prk}$: Extract pseudorandom key
\item $\text{Expand}(\text{prk}, \text{info}, L) \to \text{okm}$: Expand to $L$ bytes
\end{itemize}
\end{definition}

\begin{definition}[Authenticated Encryption (AEAD)]
An AEAD provides:
\begin{itemize}
\item $\text{Seal}(k, n, \text{aad}, pt) \to ct$: Encrypt with authentication
\item $\text{Open}(k, n, \text{aad}, ct) \to pt$: Decrypt and verify
\end{itemize}
\end{definition}

\subsection{HPKE Modes}

\subsubsection{Base Mode}

Sender encrypts to recipient's public key:

\begin{algorithm}
\caption{HPKE Base Mode Seal}
\begin{algorithmic}[1]
\Require Recipient public key $pk_R$, info, aad, plaintext $pt$
\Ensure Encapsulation $\text{enc}$, ciphertext $ct$
\State $(k_{\text{shared}}, \text{enc}) \gets \text{Encap}(pk_R)$
\State $\text{ks\_context} \gets \text{mode} \| \text{suite\_id} \| k_{\text{shared}} \| \text{info}$
\State $\text{secret} \gets \text{Extract}(\text{default\_salt}, k_{\text{shared}})$
\State $(k, n_{\text{base}}, \text{exp\_secret}) \gets \text{Expand}(\text{secret}, \text{ks\_context})$
\State $ct \gets \text{AEAD.Seal}(k, n_{\text{base}}, \text{aad}, pt)$
\State \Return $(\text{enc}, ct)$
\end{algorithmic}
\end{algorithm}

\begin{algorithm}
\caption{HPKE Base Mode Open}
\begin{algorithmic}[1]
\Require Recipient secret key $sk_R$, enc, info, aad, ciphertext $ct$
\Ensure Plaintext $pt$
\State $k_{\text{shared}} \gets \text{Decap}(\text{enc}, sk_R)$
\State $\text{ks\_context} \gets \text{mode} \| \text{suite\_id} \| k_{\text{shared}} \| \text{info}$
\State $\text{secret} \gets \text{Extract}(\text{default\_salt}, k_{\text{shared}})$
\State $(k, n_{\text{base}}, \text{exp\_secret}) \gets \text{Expand}(\text{secret}, \text{ks\_context})$
\State $pt \gets \text{AEAD.Open}(k, n_{\text{base}}, \text{aad}, ct)$
\State \Return $pt$
\end{algorithmic}
\end{algorithm}

\subsubsection{Auth Mode}

Adds sender authentication via sender's key pair:

\begin{algorithm}
\caption{HPKE Auth Mode Setup}
\begin{algorithmic}[1]
\Require Sender secret key $sk_S$, recipient public key $pk_R$
\Ensure Shared secret with sender authentication
\State $(k_{\text{shared}}, \text{enc}) \gets \text{AuthEncap}(pk_R, sk_S)$
\State Include sender's DH contribution in context
\end{algorithmic}
\end{algorithm}

\subsubsection{PSK Mode}

Incorporates pre-shared key for additional security:

\begin{algorithm}
\caption{HPKE PSK Mode Key Schedule}
\begin{algorithmic}[1]
\Require $k_{\text{shared}}$, PSK, PSK ID
\Ensure Keys derived from both ephemeral and PSK
\State $\text{psk\_input} \gets \text{PSK}$
\State $\text{ks\_context} \gets \text{mode} \| \text{suite\_id} \| k_{\text{shared}} \| H(\text{PSK\_ID})$
\State $\text{secret} \gets \text{Extract}(\text{PSK}, k_{\text{shared}})$
\end{algorithmic}
\end{algorithm}

\section{Security Analysis}

\subsection{Security Properties}

\begin{theorem}[HPKE IND-CCA2 Security]
Under the CDH assumption for the KEM's group, PRF security of HKDF, and IND-CCA2 security of the AEAD, HPKE provides IND-CCA2 security against adaptive chosen ciphertext attacks.
\end{theorem}

\begin{proof}[Sketch]
The proof proceeds via game hops:
\begin{enumerate}
\item Replace KEM shared secret with random (CDH)
\item Replace HKDF output with random (PRF)
\item IND-CCA2 of AEAD encrypting under random key
\end{enumerate}
\end{proof}

\begin{security}[Auth Mode Authenticity]
In Auth mode, only the holder of $sk_S$ can create valid encapsulations with the corresponding sender public key.
\end{security}

\begin{security}[Forward Secrecy]
HPKE provides forward secrecy: compromise of long-term keys does not compromise past session keys, as ephemeral keys are used for each encapsulation.
\end{security}

\subsection{Nonce Management}

\begin{definition}[Nonce Base Sequence]
HPKE uses a base nonce $n_{\text{base}}$ and sequence counter:
\[
n_i = n_{\text{base}} \oplus \text{seq}_i
\]
\end{definition}

\begin{proposition}[Nonce Uniqueness]
For any single HPKE context, all nonces $n_i$ are unique assuming $\text{seq}_i$ is incremented after each encryption and does not overflow.
\end{proposition}

\subsection{Implementation}

\begin{lstlisting}[language=Go]
func (p *hpkePrecompile) singleShotSeal(
    input []byte) ([]byte, error) {

    suite, err := p.parseSuite(input)
    if err != nil {
        return nil, err
    }

    // Parse recipient public key
    offset := 6
    pkLen := int(input[offset])<<8 | int(input[offset+1])
    offset += 2
    recipientPk := input[offset : offset+pkLen]
    offset += pkLen

    // Parse info, aad, plaintext
    info, aad, plaintext := parseFields(input[offset:])

    // Setup sender
    kem, _, _ := suite.Params()
    pk, err := kem.Scheme().UnmarshalBinaryPublicKey(
        recipientPk)
    if err != nil {
        return nil, err
    }

    sender, err := suite.NewSender(pk, info)
    if err != nil {
        return nil, err
    }

    enc, sealer, err := sender.Setup(nil)
    if err != nil {
        return nil, err
    }

    ciphertext, err := sealer.Seal(plaintext, aad)
    if err != nil {
        return nil, err
    }

    // Return enc || ciphertext
    result := make([]byte, len(enc)+len(ciphertext))
    copy(result, enc)
    copy(result[len(enc):], ciphertext)
    return result, nil
}
\end{lstlisting}

\subsection{Encrypted Messaging}

\begin{lstlisting}[language=Solidity]
contract EncryptedMessaging {
    mapping(address => bytes) public publicKeys;
    mapping(address => bytes[]) public encryptedMessages;

    function registerPublicKey(bytes calldata pk) external {
        publicKeys[msg.sender] = pk;
    }

    function sendEncryptedMessage(
        address recipient,
        bytes calldata info,
        bytes calldata plaintext
    ) external {
        bytes memory recipientPk = publicKeys[recipient];
        require(recipientPk.length > 0, "No public key");

        (bytes memory enc, bytes memory ct) =
            IHPKE(PRECOMPILE).singleShotSeal(
                KEMX25519, KDF_SHA256, AEAD_AES128GCM,
                recipientPk,
                info,
                "",  // no AAD
                plaintext
            );

        bytes memory envelope = abi.encodePacked(enc, ct);
        encryptedMessages[recipient].push(envelope);
    }
}
\end{lstlisting}

\section{Security Considerations}

\subsection{Key Management}

\begin{enumerate}
\item \textbf{Private Key Storage}: Never store private keys on-chain
\item \textbf{Key Rotation}: Implement key rotation for long-lived applications
\item \textbf{Domain Separation}: Use unique info parameters per application
\end{enumerate}

\subsection{Ciphertext Integrity}

HPKE's AEAD provides authentication, but:
\begin{itemize}
\item Store sender identity in AAD if attribution is needed
\item Consider replay protection via nonces or timestamps
\end{itemize}

\subsection{Side Channel Resistance}

The precompile uses constant-time operations from the CIRCL library:
\begin{itemize}
\item Constant-time scalar multiplication
\item Constant-time comparison
\item Memory access patterns independent of secrets
\end{itemize}

\section{Related Work}

\subsection{ECIES}

Elliptic Curve Integrated Encryption Scheme predates HPKE but lacks:
\begin{itemize}
\item Standardized key derivation
\item Support for authenticated modes
\item Context binding for domain separation
\end{itemize}

\subsection{NaCl box}

Libsodium's crypto\_box provides similar functionality using X25519 + XSalsa20-Poly1305. HPKE offers:
\begin{itemize}
\item Multiple cipher suite options
\item PSK and Auth modes
\item IETF standardization
\end{itemize}

\section{Conclusion}

Our HPKE precompile brings standardized hybrid encryption to the EVM, enabling new classes of privacy-preserving smart contracts. The RFC 9180 compliance ensures interoperability, while the multiple cipher suites provide flexibility for different security and performance requirements.

Future work includes:
\begin{itemize}
\item Post-quantum KEM support (Kyber/ML-KEM)
\item Streaming AEAD for large messages
\item Integration with threshold decryption
\end{itemize}
