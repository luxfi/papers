\section{Integration with Lux Quasar}

\label{sec:integration}

Corona is composed under the Lux Quasar consensus engine as the intra-lattice diversity
leg of multi-leg finality certificates. A Quasar certificate profile bundles
independently verifiable signature legs, each of which must validate for finality:

\begin{enumerate}[nosep]
\item \textbf{BLS leg}: classical BLS12-381 threshold signatures provide the fast
(1-round) aggregation lane.
\item \textbf{Pulsar leg}: threshold ML-DSA over Module-LWE (rank-$k$, FIPS~204
byte-equal, LP-4450) is the post-quantum floor.
\item \textbf{Corona leg}: this scheme---two-round Ring-LWE (rank-1)---is the
intra-lattice diversity leg, profile-selectable alongside Pulsar.
\end{enumerate}

\noindent The \textbf{Aurora} certificate profile (LP-4900) is Pulsar $\|$ Corona; the
\textbf{Polaris} profile (LP-4910) is Pulsar $\|$ Corona $\|$ Magnetar, adding the
hash-based Magnetar leg (SLH-DSA, LP-4540).

\paragraph{Diversity caveat.}
Corona and Pulsar are \emph{both} lattice constructions: Corona is the rank-1 Ring-LWE
base and Pulsar the rank-$k$ Module-LWE generalisation. The Pulsar~$\|$~Corona composition
of Aurora is therefore \emph{intra-lattice} defence-in-depth---different code paths,
different parameter sets, different rejection samplers---and is honestly \emph{not}
family-disjoint hardness: a structural break of the cyclotomic-ring lattice problem could
in principle touch both legs. True cross-family diversity is provided by the hash-based
Magnetar leg in the Polaris profile, whose security rests on hash (SLH-DSA, FIPS~205)
rather than lattices. Aurora buys implementation and parameter diversity; Polaris buys
cryptographic-family diversity.

\subsection{On-Chain Verification}

A Corona threshold signature is verified by the native EVM precompile at the raw slot
\texttt{0x012206} (LP-0120): the precompile checks the aggregated two-round signature
against the group public key in $\sim$1.6\,ms. Under the P3Q unified rollup-batch verifier
(LP-218 / LP-220) Corona is \textbf{kind byte \texttt{0x02}} at slot \texttt{0x012205};
the raw \texttt{0x012206} path remains for non-rollup-batch use.

\subsection{Permissionless Key Lifecycle}

Corona's distributed key generation (Algorithm~\ref{alg:keygen}) runs leaderless over the
\emph{current} validator set, with no trusted dealer, anchored to the Q-Chain ceremony
root $\rho$. As validators join and leave permissionlessly, the key material is reshared
across generations: each generation re-runs the DKG over the new set while holding the
group public key fixed for cross-generation verification, and snapshots are committed
on-chain. Rotation is rate-limited (a minimum dwell between rotations) and force-rotated
on an upper bound, so a churning validator set cannot exhaust the rotation machinery.
This permissionless, on-chain-anchored lifecycle---rather than any change to the
underlying two-round lattice algebra---is what adapts the academic threshold construction
to a public chain.
