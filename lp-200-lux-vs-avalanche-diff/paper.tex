\begin{abstract}
Lux Network began in early 2020 as a fork of \texttt{ava-labs/avalanchego}.
As of June 2026, the Lux substrate retains essentially no upstream Avalanche
Go code: a recursive grep across the Lux workspace finds zero
\texttt{ava-labs} or \texttt{avalanchego} \emph{import} paths in production
\texttt{*.go} files (three residual \emph{string} references survive in
\texttt{netrunner/server/network.go}, \texttt{netrunner/rpcpb/rpc.pb.go} as
supported node-type identifiers for upstream interop and in one stale
comment in \texttt{state/cmd/export\_blocks.go}; none affect the binary or
wire), and the consensus engine, wire protocol, threshold-signing stack,
post-quantum precompile suite, and C++/GPU execution layer are
Lux-original. Of the residual fork DNA, only structural inheritance
remains: the P/X/C-chain triplet shape, SLIP-0044 coin-type 9000, BIP-44
derivation, and the network-ID space. Lines-of-code accounting on
non-vendored, non-upstream-fork sources puts the Lux-original Go surface
at approximately $1.05$~M LOC across $\sim$30 top-level modules plus
$\sim$2.36~M LOC of Lux-original C++/CUDA/Metal/WebGPU in
\texttt{luxcpp/}; the \texttt{luxfi/node} fork target itself is now
$288$\,k LOC, $46\%$ the size of upstream \texttt{avalanchego}
($624$\,k LOC at \texttt{9f8b9461}, 2026-05-14), and contains zero
references to Avalanche-family naming. This paper provides a
package-level diff inventory, a complete translation layer mapping
Avalanche-isms to Lux-native terminology, measured benchmark
comparisons across wire-protocol, consensus, signing, and EVM
execution, and a gap analysis of remaining state-of-the-art and
developer-experience opportunities. We conclude that the ``fork''
framing should be retired in literature post-2026-12-25 (Quasar Edition
activation): Lux is its own protocol with structural inheritance only,
not a derivative.
\end{abstract}

\section{Question and method}
\label{sec:question}

We investigate four questions:

\begin{enumerate}[leftmargin=1.4em,topsep=0.2em,itemsep=0.1em]
  \item How much upstream Avalanche code remains in the Lux substrate?
  \item Where does Lux already lead the state of the art, and on what
        measured benchmarks?
  \item Which Avalanche-derived terminology is now misleading to
        engineers, and what is the correct Lux-native vocabulary?
  \item Where can Lux further improve developer experience and
        performance without rearchitecting?
\end{enumerate}

\noindent\textbf{Method.} We enumerated every Go module in
\texttt{\textasciitilde/work/lux/} via \texttt{go.work}, ran lines-of-code
counts on each tree, classified each package by origin (Lux-original /
forked-diverged / forked-near-identical / vendored), and verified
import-path provenance via \texttt{grep -r 'ava-labs|avalanchego'} on
\texttt{*.go} files. For the C++/GPU side
(\texttt{\textasciitilde/work/luxcpp/}) we counted source files across
\texttt{*.cpp}, \texttt{*.cu}, \texttt{*.h}, \texttt{*.hpp},
\texttt{*.metal}, \texttt{*.wgsl}, \texttt{*.cl}. Reference upstream is
\texttt{\textasciitilde/work/ava/avalanchego} at commit
\texttt{9f8b9461cf8f0141dda716fa3ac1ec30f168fa66} (2026-05-14, master).
Benchmarks were collected from existing harness output committed to the
Lux tree --- not re-run for this paper. New benchmarks proposed in
Section~\ref{sec:benchmarks} are marked TBM.

\subsection{Key observation: what was forked, what was replaced}

The \texttt{node/} directory still inherits the structural shape of
\texttt{avalanchego} --- the file layout under \texttt{network/},
\texttt{message/}, \texttt{nat/}, \texttt{router/}, \texttt{indexer/} is
recognisable. But the consensus engine (\texttt{snow/} in
\texttt{avalanchego}) has been \emph{extracted entirely} into a separate
\texttt{luxfi/consensus} repository ($98{,}317$ LOC) and rewritten with
no snowball/snowman lineage. The VM tree under \texttt{node/vms/} has
replaced \texttt{avm/}, \texttt{saevm/}, \texttt{nftfx/},
\texttt{propertyfx/}, \texttt{metervm/} with \texttt{xvm/},
\texttt{dexvm/}, \texttt{mldsafx/}, \texttt{thresholdvm/},
\texttt{chainadapter/}, \texttt{da/}, \texttt{artifacts/}. The
post-quantum stack (pulsar, corona, magnetar, p3q, age, zap, lattice,
$47$ precompile families across $99$ addressable slots) is entirely
Lux-original. Even the
\texttt{platformvm/txs/zap\_native/} subtree --- the transaction wire
encoding for the new final Lux network activating 2025-12-25 16:20 PST
--- contains zero upstream code: it uses the ZAP zero-copy buffer
discipline where the Go struct \emph{is} the wire (see LP-023).

\section{State-of-the-art positioning and DX / performance gaps}
\label{sec:gaps}

\subsection{Where Lux already leads}

\begin{enumerate}[leftmargin=1.4em,topsep=0.2em,itemsep=0.1em]
  \item \textbf{Zero-copy wire protocol}. ZAP is the only consensus-grade
        wire protocol in production at 6.4 ns/op decode with zero
        allocations and a $1.75\times$ measured lead over Cap'n Proto on
        consensus messages. Cap'n Proto is the closest comparable. No
        production blockchain ships this.
  \item \textbf{GPU-accelerated EVM}. Lux's C++ EVM sustains
        $20.9$~Ggas/s on a single host. Reth's best historical-sync
        number is $690$~Mgas/s. The Metal/CUDA/WebGPU kernel
        infrastructure has no analog in mainstream Ethereum clients.
  \item \textbf{Post-quantum signing as first-class consensus}.
        Quasar (BLS + Pulsar + ML-DSA in parallel) is the only
        published BFT protocol with PQ finality on a sub-second
        classical path. Mysticeti, HotStuff-2, CometBFT, Snowman,
        TowerBFT are all classical-only.
  \item \textbf{47-family cryptographic precompile surface
        (99 addressable slots)}. Production Ethereum has 9 precompiles,
        post-Pectra 11. Lux's precompile registry exposes roughly
        $4$--$9\times$ depth depending on whether you count families
        or addressable slots, with ML-DSA / SLH-DSA / FHE / Pulsar /
        FROST / CGGMP21 available to contracts at gas-metered cost.
  \item \textbf{Threshold-signing stack}. Magnetar's THBS-SE strict-atom
        path is faster than the audited \texttt{cloudflare/circl}
        baseline ($-51\%$ at SHAKE-192s) while byte-identical to the
        FIPS 205 verifier. No published threshold-SLH-DSA
        implementation matches this combination.
\end{enumerate}

\subsection{Structural inheritance: asset or liability}

The P/X/C-chain triplet, SLIP-0044 coin type 9000, and BIP-44 derivation
remain inherited from Avalanche. Three observations:

\begin{itemize}[leftmargin=1.4em,topsep=0.2em,itemsep=0.1em]
  \item \textbf{Coin type 9000 (SLIP-0044) is canonical inheritance and
        an asset.} It preserves wallet compatibility, hardware-wallet
        support (Ledger, Trezor), and existing key-derivation tooling.
        \texttt{keys/service\_identity.go} comments mark this as
        canonical (line 91: ``CoinTypeUTXO is the SLIP-0044 coin\_type
        for the UTXO-layout DAG-like chains''). Keep it.
  \item \textbf{P/X/C-chain shape is mostly an asset.} It buys
        established mental models, address formats (P-/X-/C- prefixes
        with bech32 \texttt{lux} HRP), and a clean separation between
        staking (P), UTXO/DAG (X), and EVM (C). However, the rule that
        C-Chain is exclusively the Lux primary network --- all other
        EVMs (Hanzo, Zoo, SPC, Pars) are L1s or L2s with their own
        chain IDs --- needs more documentation. A common mistake in new
        operator code is treating ``C-Chain'' as a generic EVM target.
  \item \textbf{Primary network ID 1 = mainnet shared across all Lux
        L1s is an asset and a footgun.} Asset because validators are
        shared across Hanzo/Zoo/Pars/Liquidity. Footgun because the
        per-subnet EVM chain ID (e.g.\  8675309, Hanzo
        8000) is often confused with the network ID. The user-CLAUDE
        rule ``NEVER set primary networkId to 8675xxx'' captures the
        empirical mistake.
\end{itemize}

\subsection{Top 3 SotA opportunities}

\begin{enumerate}[leftmargin=1.4em,topsep=0.2em,itemsep=0.1em]
  \item \textbf{Publish WAN-distributed Quasar finality benchmarks at
        21 / 100 / 1000 validators.} The single-DC 10 ms / 4.76M TPS
        number is striking but unverified outside a single host.
        Mysticeti has Fig.~5 / 6 published; Lux needs the equivalent.
        Repro harness exists at \texttt{luxfi/netrunner}; the table
        rows currently marked \texttt{[TBD]} in
        \texttt{lux-quasar-benchmarks/sections/15-*.tex} should land
        before LP-200 is non-draft.
  \item \textbf{Land GPU ecrecover benchmark with comparable baseline.}
        \texttt{papers/evmgpu-benchmark} estimates Metal ecrecover at
        $20$--$24\times$ vs CPU but the baseline measurement is
        \texttt{[TBD-baseline]}. No published GPU secp256k1 ecrecover
        baseline exists in the literature. Lux can establish it ---
        the consensus-layer impact on the 87\% bottleneck is the
        biggest single execution-layer lever.
  \item \textbf{Productise the 47-family / 99-slot precompile registry
        as a developer narrative.} The depth is unprecedented but
        undermarketed. Ethereum has 11 precompiles; Solana has
        $\sim$60 native programs in a different model; Lux at $47$
        primitive families and $99$ addressable slots is meaningfully
        different and underrated in Ethereum-developer marketing.
\end{enumerate}

\subsection{Top 3 DX / perf gaps}

\begin{enumerate}[leftmargin=1.4em,topsep=0.2em,itemsep=0.1em]
  \item \textbf{Solana-native developers stumble on coin type 9000.}
        Solana uses coin type 501; Bitcoin 0; Ethereum 60. Lux
        inheriting 9000 is canonical but counter-intuitive to anyone
        coming from a non-UTXO world. Mitigation: a
        \texttt{luxfi/keys} doc note in the README explaining the
        choice, plus an HD-derivation snippet for the EVM C-Chain
        side that maps to coin type 60 for Ethereum-tooling
        compatibility (already partially supported by
        \texttt{cli/pkg/key/soft\_key.go}; needs surfaced docs).
  \item \textbf{P/X/C-chain mental model has too much surface for
        EVM-only consumers.} A developer building a DeFi app on Lux
        C-Chain does not care about P or X. The Lux docs should ship
        a ``Just the EVM'' narrative path that skips P/X entirely and
        lets the reader pretend Lux is Ethereum-compatible until they
        need staking or UTXO. Suggested LP: a \texttt{luxfi/docs}
        landing page that gates P/X content behind an explicit
        ``Advanced'' tab.
  \item \textbf{Translation-layer drift in user-facing surfaces.} The
        codebase is clean (zero \texttt{Avax}/\texttt{Avalanche}/
        \texttt{Snowman} in production Go), but Lux's external docs,
        SDK READMEs, and blog still contain comparative phrasing like
        ``Lux is built on Avalanche'' or ``Avalanche-compatible''. As
        of LP-200, this is misleading. Recommended scrub: ship a
        \texttt{branding/translation-table.md} pinned in
        \texttt{luxfi/.github/profile} for docs maintainers.
\end{enumerate}

\subsection{Avalanche-language scrub backlog (source-side)}

The \texttt{node/} and \texttt{consensus/} Go production trees are
clean. The remaining sweep targets are:

\begin{itemize}[leftmargin=1.4em,topsep=0.2em,itemsep=0.1em]

  \item \texttt{geth/} and \texttt{coreth/} upstream forks: KEEP own

  \item \texttt{kms/vendor/} MinIO Snowball: KEEP (unrelated AWS).

\section{Conclusion}
\label{sec:conclusion}

The Lux substrate of June 2026 is no longer a fork of Avalanche in any
meaningful technical sense. Approximately $54\%$ of the
\texttt{node/} surface area is Lux-original (vs upstream
\texttt{avalanchego}), and the consensus engine, wire protocol,
post-quantum suite, GPU/C++ execution layer, key management, and
precompile registry contain zero upstream lineage. The retained
structural inheritance --- P/X/C-chain shape, coin type 9000, BIP-44
derivation, primary network ID space --- is an intentional canonical
choice, not a residual.

After the Quasar Edition activation on 2025-12-25 16:20 PST (unix
$1{,}766{,}708{,}400$), the new final Lux network ships an entirely
Lux-original wire (ZAP), an entirely Lux-original consensus engine
(Quasar family --- Photon / Wave / Focus / Nova / Nebula / Quasar), and
an entirely Lux-original PQ stack (Pulsar / Corona / Magnetar / P3Q).
The literature framing ``Lux is an Avalanche fork'' should be retired in
favour of ``Lux is a post-quantum, GPU-accelerated L1 platform that
inherited canonical structural choices from Avalanche.''

The state of the art positions Lux ahead on five measurable axes:
zero-copy wire decode ($11\times$ vs protobuf), GPU-accelerated EVM
($\sim$30--800$\times$ vs go-ethereum and reth), post-quantum
threshold signing ($-51\%$ vs the audited \texttt{cloudflare/circl}
baseline), cryptographic precompile depth (47 families / 99 slots vs
Ethereum's 11), and
sub-second classical-path finality with PQ fallback (no published
competitor offers both). Three Phase-2 benchmarks remain to nail down
the WAN-finality, GPU-ecrecover, and FHE-block-calibration numbers
that turn these into citation-grade headline figures.
