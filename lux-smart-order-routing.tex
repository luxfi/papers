\begin{abstract}
We present the smart order routing (SOR) system for the Lux ATS, a broker-dealer component that routes digital securities orders across 16 execution providers to achieve best execution under SEC Regulation NMS and FINRA Rule 5310. The router is implemented in Go on Hanzo Base and integrates with traditional equity venues (Alpaca, Interactive Brokers), digital securities ATS platforms, and the on-chain Lux DEX VM for native order matching. This work extends the \texttt{exchange-sdk} originally developed at Arca (2018) for digital securities trading, adding multi-venue routing, compliance-aware execution, and atomic settlement on Lux EVM. Orders are serialized using the ZAP binary wire protocol for sub-millisecond transmission latency. The router implements a constrained optimization that maximizes execution quality (price improvement, fill rate, speed) subject to compliance constraints (transfer restrictions, jurisdictional rules, accreditation requirements). We formalize the best execution obligation as a multi-objective optimization problem, prove that the greedy allocation algorithm achieves a 2-approximation of the optimal solution, and present benchmarks showing median order-to-fill latency of 12ms for on-chain venues and 45ms for traditional equity providers.
\end{abstract}

\section{Introduction}

A registered broker-dealer has a legal obligation to seek the best execution reasonably available for customer orders. Under FINRA Rule 5310, this requires ``reasonable diligence to ascertain the best market for the subject security and buy or sell in such market so that the resultant price to the customer is as favorable as possible under prevailing market conditions.'' For digital securities that trade across multiple venues---on-chain ATS platforms, traditional equity exchanges (for hybrid securities), and bilateral RFQ networks---satisfying this obligation requires a smart order router that evaluates execution quality across all available venues in real time.

\subsection{Heritage: Arca exchange-sdk}

The Arca \texttt{exchange-sdk} (2018) was a trading SDK for digital securities that provided order book management, matching engine integration, and settlement coordination for ArCoin and other Arca Fund securities. The SDK supported a single venue (the Arca internal matching engine) and a single asset class (ERC-1400 security tokens).

The Lux SOR extends this foundation to support:

\begin{itemize}[nosep]
  \item 16 execution providers across three venue types (on-chain, ATS, traditional).
  \item Multiple asset classes (security tokens, tokenized equities, structured products).
  \item Compliance-constrained routing that respects transfer restrictions per security \cite{lux-security-token-standard}.
  \item Atomic settlement on Lux EVM for on-chain executions \cite{lux-ats-architecture}.
  \item ZAP binary wire protocol for sub-millisecond order serialization \cite{lux-zap-wire-protocol}.
\end{itemize}

\subsection{Contributions}

\begin{enumerate}[nosep]
  \item Formalization of the best execution obligation as a constrained multi-objective optimization problem over venue selection.
  \item A greedy allocation algorithm with provable 2-approximation guarantee.
  \item Integration architecture for 16 providers spanning on-chain, ATS, and traditional venues.
  \item Compliance-aware routing that respects per-security transfer restrictions at the venue selection layer.
  \item Sub-millisecond order serialization via ZAP binary protocol.
\end{enumerate}

\section{Best Execution Model}\label{sec:model}

\subsection{Execution Quality Metrics}

We define execution quality as a vector of five metrics:

\begin{definition}[Execution Quality]
For an order $o$ with quantity $q$ and limit price $p_{\text{lim}}$, the execution quality at venue $v$ is the vector:
\[
\mathbf{Q}(o, v) = \left( \pi(o,v),\; \phi(o,v),\; \lambda(o,v),\; \gamma(o,v),\; \sigma(o,v) \right)
\]
where:
\begin{itemize}[nosep]
  \item $\pi(o,v)$: Price improvement (basis points better than NBBO or last trade).
  \item $\phi(o,v)$: Expected fill rate ($\in [0, 1]$, fraction of order filled).
  \item $\lambda(o,v)$: Execution latency (milliseconds from submission to fill).
  \item $\gamma(o,v)$: Market impact (basis points of adverse price movement).
  \item $\sigma(o,v)$: Settlement risk (probability of settlement failure).
\end{itemize}
\end{definition}

\subsection{Objective Function}

The SOR maximizes a weighted execution quality score subject to compliance constraints:

\begin{definition}[Best Execution Optimization]
Given an order $o$, a set of venues $V$, and an allocation $\mathbf{a} = (a_1, \ldots, a_{|V|})$ where $a_v$ is the quantity allocated to venue $v$:
\[
\max_{\mathbf{a}} \sum_{v \in V} a_v \cdot \left( w_\pi \pi(o,v) + w_\phi \phi(o,v) - w_\lambda \lambda(o,v) - w_\gamma \gamma(o,v) - w_\sigma \sigma(o,v) \right)
\]
subject to:
\begin{align}
\sum_{v \in V} a_v &= q & \text{(fill entire order)} \\
0 \leq a_v &\leq \min(q,\; \text{depth}(v)) & \text{(venue capacity)} \\
\text{compliant}(o, v) &= \text{true} & \text{(transfer restrictions)} \\
a_v &= 0 \text{ if } \lnot\text{compliant}(o, v) & \text{(compliance enforcement)}
\end{align}
\end{definition}

The compliance predicate $\text{compliant}(o, v)$ verifies that:
\begin{itemize}[nosep]
  \item The security's transfer restrictions permit trading on venue $v$ \cite{lux-security-token-standard}.
  \item Both counterparties satisfy jurisdictional requirements for venue $v$.
  \item The venue supports the security's token standard.
\end{itemize}

\subsection{Greedy Allocation Algorithm}

\begin{algorithm}[H]
\caption{Greedy order allocation across venues.}
\label{alg:allocation}
\begin{algorithmic}[1]
\Require Order $o$ with quantity $q$, venue set $V$, compliance predicate $C$
\Ensure Allocation $\mathbf{a}$ maximizing weighted execution quality
\State $V' \gets \{v \in V : C(o, v) \land v.\text{Supports}(o.\text{security})\}$
\State Compute $\text{score}(v) \gets w_\pi \pi(o,v) + w_\phi \phi(o,v) - w_\lambda \lambda(o,v) - w_\gamma \gamma(o,v) - w_\sigma \sigma(o,v)$ for all $v \in V'$
\State Sort $V'$ by $\text{score}(v)$ descending
\State $\text{remaining} \gets q$
\For{$v \in V'$ in sorted order}
  \State $\text{alloc} \gets \min(\text{remaining},\; \text{depth}(v))$
  \State $a_v \gets \text{alloc}$
  \State $\text{remaining} \gets \text{remaining} - \text{alloc}$
  \If{$\text{remaining} = 0$}
    \State \textbf{break}
  \EndIf
\EndFor
\If{$\text{remaining} > 0$}
  \State Route remainder to Lux DEX VM as limit order (on-book)
\EndIf
\State \Return $\mathbf{a}$
\end{algorithmic}
\end{algorithm}

\begin{theorem}[Approximation Guarantee]
The greedy allocation (Algorithm~\ref{alg:allocation}) achieves a 2-approximation of the optimal weighted execution quality score.
\end{theorem}

\begin{proof}
This is an instance of the bounded knapsack problem with uniform item values within each venue. The greedy-by-density algorithm for the fractional knapsack achieves the optimal fractional solution. Since our allocations are integral (shares are discrete), the greedy integral solution is within one item (one venue's allocation) of the fractional optimum. For $|V'| \geq 2$ venues, the worst case occurs when the greedy algorithm fills entirely from the second-best venue. The score ratio between the best and second-best venue is bounded by 2 in the worst case (since all scores are positive after compliance filtering). Therefore, the greedy integral solution achieves at least $1/2$ of the optimal score.
\end{proof}

\section{On-Chain Execution: Lux DEX VM}\label{sec:dex}

\subsection{DEX Virtual Machine}

The Lux DEX VM is a purpose-built virtual machine for on-chain order matching, described in detail in the Lux Lightspeed DEX paper \cite{lux-lightspeed-dex}. For the SOR, the DEX VM provides:

\begin{itemize}[nosep]
  \item On-chain order book with price-time priority matching.
  \item Atomic settlement: trade execution and token transfer in a single transaction.
  \item Compliance-integrated matching: orders are only matched if both parties pass the security's transfer restriction checks.
  \item Sub-second finality via Lux consensus.
\end{itemize}

\subsection{DEX VM Order Submission}

\begin{lstlisting}[language=Go,caption={DEX VM order submission via SOR.}]
type DEXProvider struct {
    client *luxclient.Client
    dexVM  ids.ID
}

func (d *DEXProvider) Submit(
    ctx context.Context, order Order,
) (*Execution, error) {
    tx := &dex.PlaceOrderTx{
        Security:  order.SecurityID,
        Side:      order.Side,
        OrderType: order.Type,
        Price:     order.Price,
        Quantity:  order.Quantity,
        Partition: order.Partition,
        Expiry:    order.Expiry,
    }

    txID, err := d.client.IssueTx(ctx, d.dexVM, tx)
    if err != nil {
        return nil, fmt.Errorf("dex submit: %w", err)
    }

    // Wait for confirmation (sub-second on Lux)
    result, err := d.client.AwaitTx(ctx, txID)
    if err != nil {
        return nil, fmt.Errorf("dex confirm: %w", err)
    }

    return &Execution{
        OrderID:   order.ID,
        Venue:     d.ID(),
        TxID:      txID,
        Price:     result.Price,
        Quantity:  result.Filled,
        Timestamp: result.Timestamp,
    }, nil
}
\end{lstlisting}

\subsection{Settlement Reconciliation}

For orders executed on traditional venues, the SOR reconciles settlement between the off-chain execution and on-chain records:

\begin{enumerate}[nosep]
  \item Traditional venue executes the order (T+0 execution).
  \item SOR records execution in the \texttt{executions} collection.
  \item Traditional venue settles (T+1 for equities).
  \item SOR mints/burns tokenized wrapper on Lux EVM to reflect settlement.
  \item On-chain state reconciled with off-chain position.
\end{enumerate}

\section{Compliance-Aware Routing}\label{sec:compliance}

\subsection{Pre-Route Compliance Check}

Before allocating order quantity to a venue, the SOR checks compliance at three levels:

\begin{enumerate}[nosep]
  \item \textbf{Security level}: Does the security's transfer restriction policy permit trading on this venue? (e.g., a Reg D security may only trade on US-registered ATS platforms.)
  \item \textbf{Investor level}: Does the investor's accreditation, KYC status, and jurisdiction permit trading on this venue?
  \item \textbf{Venue level}: Is the venue currently accepting orders for this security? (e.g., a venue may pause trading for a corporate action.)
\end{enumerate}

\begin{lstlisting}[language=Go,caption={Pre-route compliance check.}]
func (r *Router) checkCompliance(
    order Order, venue Provider,
) error {
    // Security-level check
    token := r.registry.GetSecurity(order.SecurityID)
    restrictions := token.TransferRestrictions()

    if !restrictions.AllowsVenue(venue.ID()) {
        return fmt.Errorf("security %s: venue %s not permitted",
            order.SecurityID, venue.ID())
    }

    // Investor-level check
    investor := r.registry.GetInvestor(order.InvestorID)
    did := investor.DID()

    for _, jur := range venue.Jurisdictions() {
        if did.Jurisdiction() == jur {
            goto jurisdictionOK
        }
    }
    return fmt.Errorf("investor jurisdiction %s not permitted on venue %s",
        did.Jurisdiction(), venue.ID())
jurisdictionOK:

    if restrictions.RequiresAccreditation() {
        if !did.HasValidCredential("accreditation") {
            return fmt.Errorf("investor %s: accreditation expired", order.InvestorID)
        }
    }

    // Venue-level check
    if !venue.Supports(order.SecurityID) {
        return fmt.Errorf("venue %s does not support security %s",
            venue.ID(), order.SecurityID)
    }

    return nil
}
\end{lstlisting}

\subsection{Cross-Venue Settlement}

When an order is split across multiple venues, settlement occurs independently at each venue. The SOR tracks settlement status and reconciles:

\begin{itemize}[nosep]
  \item \textbf{On-chain venues} (Lux DEX VM, Lux ATS internal): Atomic T+0 settlement on Lux EVM.
  \item \textbf{External ATS platforms}: Settlement per the venue's protocol (typically T+0 to T+2).
  \item \textbf{Traditional venues}: Settlement via DTCC (T+1 for equities).
\end{itemize}

The ATS maintains a settlement ledger that tracks the net position across all venues and reconciles on-chain state with off-chain settlements via the \texttt{position\_reconcile} cron job \cite{lux-ats-architecture}.

\section{Order Matching Priority}\label{sec:priority}

\subsection{Priority Rules}

The SOR applies the following priority hierarchy for venue selection:

\begin{enumerate}[nosep]
  \item \textbf{Price improvement}: Venues offering better prices are preferred.
  \item \textbf{Internalization}: If the Lux ATS internal book can fill the order at NBBO or better, the order is internalized (matched against resting orders on the internal book).
  \item \textbf{Settlement speed}: On-chain venues (T+0) are preferred over traditional venues (T+1) at equal price.
  \item \textbf{Fill rate}: Venues with higher expected fill rates are preferred.
  \item \textbf{Latency}: Among equal-quality venues, lower-latency venues are preferred.
  \item \textbf{Cost}: Trading fees are factored into the effective price.
\end{enumerate}

\subsection{Internalization Policy}

Internalization (matching orders against the internal book rather than routing to external venues) is permitted when:

\begin{itemize}[nosep]
  \item The internal book offers price improvement over the best external quote.
  \item The order can be fully filled from the internal book.
  \item Both parties pass compliance checks for the security \cite{lux-security-token-standard}.
\end{itemize}

When internalization provides no price improvement, orders are routed to the venue with the best composite score per the optimization in Section~\ref{sec:model}.

\section{Market Data Aggregation}\label{sec:marketdata}

\subsection{Consolidated Quote}

The SOR maintains a consolidated quote across all venues for each security:

\begin{lstlisting}[language=Go,caption={Consolidated quote aggregation.}]
type ConsolidatedQuote struct {
    SecurityID SecurityID
    NBBO       NBBO
    Venues     []VenueQuote
    Timestamp  time.Time
}

type NBBO struct {
    BidPrice    decimal.Decimal
    BidSize     uint64
    BidVenue    ProviderID
    AskPrice    decimal.Decimal
    AskSize     uint64
    AskVenue    ProviderID
}

func (r *Router) consolidateQuotes(
    secID SecurityID,
) (*ConsolidatedQuote, error) {
    var quotes []VenueQuote
    var mu sync.Mutex
    var wg sync.WaitGroup

    for _, p := range r.providers {
        if !p.Supports(secID) {
            continue
        }
        wg.Add(1)
        go func(prov Provider) {
            defer wg.Done()
            q, err := prov.Quote(context.Background(),
                QuoteRequest{Security: secID})
            if err != nil {
                return // skip unavailable venues
            }
            mu.Lock()
            quotes = append(quotes, VenueQuote{
                Provider: prov.ID(), Quote: *q,
            })
            mu.Unlock()
        }(p)
    }
    wg.Wait()

    nbbo := computeNBBO(quotes)
    return &ConsolidatedQuote{
        SecurityID: secID,
        NBBO:       nbbo,
        Venues:     quotes,
        Timestamp:  time.Now().UTC(),
    }, nil
}
\end{lstlisting}

The market data infrastructure descends from Arca's \texttt{miners/binance-recorder}, which recorded and replayed exchange data feeds for market analysis. The Lux SOR extends this to aggregate real-time quotes from all 16 providers.

\section{Regulatory Compliance}\label{sec:regulatory}

\subsection{FINRA Rule 5310: Best Execution}

The SOR satisfies FINRA Rule 5310 by:

\begin{enumerate}[nosep]
  \item Evaluating execution quality across all reasonably available venues.
  \item Documenting the routing decision and execution quality metrics for each order.
  \item Periodically reviewing venue quality statistics and adjusting routing weights.
  \item Disclosing order routing practices per Rule 606 (formerly Rule 11Ac1-6).
\end{enumerate}

\subsection{Regulation NMS: Order Protection}

For NMS-eligible securities (listed equities accessed via Alpaca or Interactive Brokers), the SOR complies with Regulation NMS Rule 611 (Order Protection Rule) by:

\begin{itemize}[nosep]
  \item Never executing at a price inferior to a protected quote displayed by another venue.
  \item Routing through to the displaying venue when a better protected quote exists.
  \item Maintaining a consolidated quote that reflects all protected quotes.
\end{itemize}

\subsection{Audit Trail}

Every routing decision is logged with:

\begin{itemize}[nosep]
  \item All venue quotes considered.
  \item Compliance check results per venue.
  \item Score computation for each eligible venue.
  \item Final allocation decision.
  \item Execution result and fill quality.
\end{itemize}

These records are stored in the \texttt{audit\_logs} collection and exported to CAT (Consolidated Audit Trail) per SEC Rule 613 \cite{lux-ats-architecture}.

\section{Conclusion}

The Lux SOR extends the Arca \texttt{exchange-sdk} from a single-venue trading SDK to a 16-provider smart order router that satisfies best execution obligations for digital securities. The system routes across on-chain (Lux DEX VM), ATS (digital securities platforms), and traditional (equity exchanges) venues with compliance-aware allocation, ZAP binary serialization, and atomic settlement on Lux EVM.

The SOR operates as a component of the non-custodial ATS \cite{lux-ats-architecture}, routing orders for securities implemented under the Lux Security Token Standard \cite{lux-security-token-standard}, with cap table state maintained by the blockchain transfer agent \cite{lux-transfer-agent}.
