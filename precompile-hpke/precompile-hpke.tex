\begin{abstract}
We specify the Hybrid Public Key Encryption (HPKE) precompile on the Lux EVM,
implementing RFC~9180 with the cipher suite DHKEM(X25519, HKDF-SHA256),
HKDF-SHA256, ChaCha20Poly1305. HPKE is a composable framework for public-key
encryption that cleanly separates key encapsulation (KEM), key derivation (KDF),
and authenticated encryption (AEAD). The precompile provides four HPKE modes:
Base (no authentication), PSK (pre-shared key), Auth (sender authentication),
and AuthPSK (both). Gas cost: 8\,000 base plus 7 gas per byte of plaintext.
HPKE is the encryption layer for MLS (Messaging Layer Security, RFC~9420),
TLS Encrypted Client Hello, and Oblivious HTTP (RFC~9458).
\end{abstract}

\section{Introduction}

HPKE~\cite{rfc9180} standardizes hybrid public-key encryption into a single
interoperable protocol. Unlike raw ECIES, HPKE provides:
\begin{itemize}
  \item Negotiable cipher suites (KEM, KDF, AEAD triples).
  \item Sender authentication modes (Auth, AuthPSK).
  \item Export-only mode for key derivation without encryption.
  \item Context for sequential encryption (AEAD sequence numbers).
\end{itemize}

On-chain HPKE enables:
\begin{enumerate}[label=(\roman*)]
  \item MLS group key derivation for on-chain messaging groups.
  \item Encrypted Client Hello (ECH) for DNS-over-HTTPS privacy.
  \item Oblivious HTTP relay verification.
  \item Standard-compliant encryption between smart contracts and off-chain services.
\end{enumerate}

\section{Cipher Suite}

The precompile implements a single cipher suite:
\begin{itemize}
  \item \textbf{KEM}: DHKEM(X25519, HKDF-SHA256) --- X25519 key agreement
    with HKDF-SHA256 for shared secret extraction.
  \item \textbf{KDF}: HKDF-SHA256 --- key derivation for encryption keys and nonces.
  \item \textbf{AEAD}: ChaCha20Poly1305 --- authenticated encryption.
\end{itemize}

This matches the mandatory-to-implement suite for MLS and is the most
widely deployed HPKE configuration.

\subsection{Single-Shot Seal}

\textbf{Input}: Selector (1), mode (1), recipient public key (32 bytes),
info string length (2 bytes), info string, AAD length (2 bytes), AAD,
entropy (32 bytes), plaintext.

\textbf{Output}: Encapsulated key $enc$ (32 bytes) $\|$ ciphertext $\|$ tag (16 bytes).

The single-shot operation performs SetupBaseS + Seal in one call for the
common case of encrypting a single message.

\section{Security Analysis}

\subsection{IND-CCA2}

HPKE Base mode achieves IND-CCA2 under the gap-CDH assumption on X25519 and
the PRF security of HKDF-SHA256.

\subsection{Insider Security}

Auth mode provides insider security: an adversary with a corrupted sender key
cannot decrypt messages intended for the receiver. This is stronger than the
``outsider security'' of ECIES.

\subsection{Context Binding}

The \texttt{info} parameter binds the encryption context to a specific protocol
or application. This prevents cross-protocol attacks where a ciphertext encrypted
for one purpose is replayed in another context.

\subsection{Sequence Numbers}

For multi-message contexts (SetupBaseS/R followed by multiple Seal/Open),
HPKE maintains an internal sequence counter used as the AEAD nonce. This
ensures nonce uniqueness without caller management. However, on-chain state
management for multi-message contexts requires the contract to track the
context state between transactions.

\section{Conclusion}

The HPKE precompile provides RFC~9180 compliant hybrid public-key encryption on
the Lux EVM. As the encryption layer for MLS, ECH, and OHTTP, HPKE represents
the IETF consensus on how public-key encryption should be composed. The
precompile avoids the ad-hoc KEM-DEM construction of ECIES by using a
standardized, formally analyzed framework.
