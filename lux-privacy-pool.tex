\begin{abstract}
We present Lux Privacy Pools, a compliant transaction privacy system that enables users to transact privately while proving they are not associated with sanctioned or illicit addresses. The design extends the Privacy Pool framework of Buterin et al.\ to the Lux Network's multi-chain architecture, using zero-knowledge proofs to demonstrate membership in curated ``association sets'' of compliant depositors without revealing which specific deposit a withdrawal corresponds to. Users deposit tokens into a privacy pool contract, which commits deposits to a Merkle tree. To withdraw, a user generates a zero-knowledge proof showing: (i)~knowledge of a valid deposit in the Merkle tree (spend authorization); (ii)~that the deposit is a member of an association set $\mathcal{A}$ of compliant addresses (regulatory compliance); and (iii)~that the withdrawal nullifier is fresh (double-spend prevention). We formalize the association set model, define the roles of Association Set Providers (ASPs), and prove that the system achieves indistinguishability of withdrawals within an association set while preventing illicit fund mixing. The construction uses Groth16 zk-SNARKs over BLS12-381, achieving proof generation in 2.8 seconds on consumer hardware and on-chain verification in 326,000 gas via Lux's BLS12-381 precompile. We prove the system is sound (no withdrawal without a valid deposit), zero-knowledge (no information leakage beyond association set membership), and complete (honest users can always withdraw). We analyze the privacy--compliance tradeoff, showing that larger association sets provide stronger privacy guarantees while maintaining regulatory compatibility.
\end{abstract}

\section{Introduction}

Blockchain transaction privacy and regulatory compliance have been viewed as fundamentally opposed goals. Privacy-preserving protocols like Tornado Cash \cite{pertsev2019tornado} provide strong anonymity but make it impossible to distinguish legitimate privacy-seeking users from money launderers. This led to regulatory action, including OFAC sanctions against Tornado Cash addresses \cite{ofac2022tornado}.

Privacy Pools, proposed by Buterin, Illum, Nazeri, Wahrstatter, and Jain \cite{buterin2023privacy}, offer a middle path: users can prove their deposits belong to a curated set of compliant addresses (the ``association set'') without revealing which specific deposit they are withdrawing. This preserves transaction privacy within the compliant set while allowing regulators to verify that funds did not originate from sanctioned sources.

Lux Privacy Pools adapt this framework to the Lux Network with the following innovations:

\begin{enumerate}[label=(\roman*)]
    \item \textbf{Multi-chain privacy}: Privacy pools span multiple Lux appchains via Warp Messaging, enabling cross-chain private transfers.
    \item \textbf{BLS12-381 integration}: Groth16 proofs verified via Lux's native BLS12-381 precompile at 326,000 gas.
    \item \textbf{Association Set Providers (ASPs)}: A decentralized marketplace of compliance oracles producing signed association sets.
    \item \textbf{Tiered privacy}: Multiple association set granularities from ``all non-sanctioned'' (maximum privacy) to ``KYC-verified'' (maximum compliance).
    \item \textbf{Incremental Merkle tree}: Efficient deposit accumulation supporting millions of deposits with $O(\log n)$ proof size.
\end{enumerate}

\section{System Model}\label{sec:model}

\subsection{Participants}

\begin{definition}[Privacy Pool Roles]
\begin{itemize}
    \item \textbf{Depositors}: Users who deposit tokens into the privacy pool.
    \item \textbf{Withdrawers}: Users who withdraw tokens from the pool (may be the same or different address as the depositor).
    \item \textbf{Association Set Providers (ASPs)}: Entities that curate and publish association sets of compliant deposit commitments.
    \item \textbf{Verifiers}: On-chain smart contracts that verify zero-knowledge proofs.
    \item \textbf{Regulators}: Off-chain entities that define compliance criteria for ASPs.
\end{itemize}
\end{definition}

\subsection{Cryptographic Building Blocks}

\begin{definition}[Commitment Scheme]
We use a Pedersen commitment over the Jubjub curve (embedded in BLS12-381):
\begin{equation}
    \mathsf{Commit}(v, r) = v \cdot G + r \cdot H
\end{equation}
where $v$ is the deposited amount, $r$ is a random blinding factor, and $G, H$ are independent generators.
\end{definition}

\begin{definition}[Nullifier]
Each deposit has a unique nullifier:
\begin{equation}
    \mathsf{nf} = H_{\text{null}}(\mathsf{sk}, \mathsf{leafIndex})
\end{equation}
where $\mathsf{sk}$ is the depositor's secret key and $\mathsf{leafIndex}$ is the deposit's position in the Merkle tree. Publishing the nullifier on withdrawal prevents double-spending without revealing the deposit.
\end{definition}

\begin{definition}[Incremental Merkle Tree]
Deposits are accumulated in a Merkle tree of depth $d = 20$ (capacity: $2^{20} \approx 1{,}048{,}576$ deposits). The tree root $R$ commits to all deposits:
\begin{equation}
    R = \mathsf{MerkleRoot}(\mathsf{leaf}_0, \mathsf{leaf}_1, \ldots, \mathsf{leaf}_{n-1})
\end{equation}
where each $\mathsf{leaf}_i = H(\mathsf{Commit}(v_i, r_i), \mathsf{pk}_i)$.
\end{definition}

\section{Association Sets}\label{sec:association}

\subsection{Definition}

\begin{definition}[Association Set]
An association set $\mathcal{A} \subseteq \{0, 1, \ldots, n-1\}$ is a subset of deposit indices deemed compliant by an ASP. The ASP publishes the Merkle root of $\mathcal{A}$:
\begin{equation}
    R_{\mathcal{A}} = \mathsf{MerkleRoot}(\{\mathsf{leaf}_i : i \in \mathcal{A}\})
\end{equation}
\end{definition}

\subsection{Association Set Properties}

An association set must satisfy:
\begin{enumerate}
    \item \textbf{Inclusion}: $\mathcal{A} \subseteq \{0, \ldots, n-1\}$ (only actual deposits).
    \item \textbf{Non-empty}: $|\mathcal{A}| \geq k_{\min}$ (minimum anonymity set size).
    \item \textbf{Exclusion of sanctioned}: No deposit from a sanctioned address is in $\mathcal{A}$.
    \item \textbf{Timeliness}: $\mathcal{A}$ is updated within $\Delta_{\text{update}}$ epochs of new sanctions.
\end{enumerate}

\subsection{ASP Marketplace}

ASPs compete in a marketplace:

\begin{algorithm}[H]
\caption{ASP Registration and Set Publication}
\label{alg:asp}
\begin{algorithmic}[1]
\Procedure{RegisterASP}{aspAddress, criteria, bond}
    \State \textbf{require} $\mathsf{bond} \geq 10{,}000$ LUX
    \State Record ASP with compliance criteria
    \State ASP begins monitoring deposits
\EndProcedure
\Procedure{PublishSet}{$\mathcal{A}$, epoch}
    \State Compute $R_{\mathcal{A}} \gets \mathsf{MerkleRoot}(\{\mathsf{leaf}_i : i \in \mathcal{A}\})$
    \State Sign $\sigma \gets \mathsf{Sign}(\mathsf{sk}_{\text{ASP}}, R_{\mathcal{A}} \| \mathsf{epoch})$
    \State Publish $(R_{\mathcal{A}}, \mathsf{epoch}, \sigma)$ on-chain
\EndProcedure
\end{algorithmic}
\end{algorithm}

If an ASP includes a sanctioned deposit in its set, challengers can slash the ASP's bond:

\begin{definition}[ASP Slashing]
A challenge $(\mathsf{depositIdx}, \mathsf{sanctionProof})$ against ASP with set $\mathcal{A}$ succeeds if:
\begin{enumerate}
    \item $\mathsf{depositIdx} \in \mathcal{A}$ (Merkle proof of inclusion in $R_{\mathcal{A}}$).
    \item The deposit address is sanctioned ($\mathsf{sanctionProof}$ from oracle).
\end{enumerate}
On successful challenge: ASP bond slashed (50\% to challenger, 50\% burned).
\end{definition}

\section{Zero-Knowledge Proof System}\label{sec:zk}

\subsection{Circuit Description}

The withdrawal proof circuit $\mathcal{C}$ enforces four properties:

\begin{definition}[Privacy Pool ZK Circuit]
Public inputs: $(R, R_{\mathcal{A}}, \mathsf{nf}, \mathsf{recipient}, v)$\\
Private inputs: $(\mathsf{sk}, r, \mathsf{leafIndex}, \mathsf{merklePath}, \mathsf{assocPath})$

The circuit verifies:
\begin{enumerate}
    \item \textbf{Deposit existence}: $\mathsf{leaf} = H(\mathsf{Commit}(v, r), \mathsf{pk})$ is in the Merkle tree with root $R$ at path $\mathsf{merklePath}$.
    \item \textbf{Key ownership}: $\mathsf{pk} = \mathsf{sk} \cdot G$ (the prover knows the secret key).
    \item \textbf{Nullifier correctness}: $\mathsf{nf} = H_{\text{null}}(\mathsf{sk}, \mathsf{leafIndex})$.
    \item \textbf{Association set membership}: $\mathsf{leaf}$ is in the association set Merkle tree with root $R_{\mathcal{A}}$ at path $\mathsf{assocPath}$.
\end{enumerate}
\end{definition}

\subsection{Hash Function Selection}

We use Poseidon \cite{grassi2021poseidon} as the in-circuit hash function, optimized for arithmetic circuits:

\begin{definition}[Poseidon Hash]
Poseidon is an algebraic hash function over $\mathbb{F}_p$ (the BLS12-381 scalar field) with:
\begin{itemize}
    \item Width: $t = 3$ (2 inputs + 1 capacity)
    \item Full rounds: $R_f = 8$
    \item Partial rounds: $R_p = 57$
    \item Security: 128-bit against algebraic and statistical attacks
\end{itemize}
Poseidon requires $\sim$300 R1CS constraints per hash, versus $\sim$25,000 for SHA-256 in a circuit.
\end{definition}

\section{Protocol Specification}\label{sec:protocol}

\subsection{Deposit}

\begin{algorithm}[H]
\caption{Privacy Pool Deposit}
\label{alg:deposit}
\begin{algorithmic}[1]
\Procedure{Deposit}{user, amount $v$}
    \State \textbf{require} $v \in \{0.1, 1, 10, 100, 1000\}$ LUX \Comment{Fixed denominations}
    \State User generates: $\mathsf{sk} \xleftarrow{\$} \mathbb{F}_p$, $r \xleftarrow{\$} \mathbb{F}_p$
    \State $\mathsf{pk} \gets \mathsf{sk} \cdot G$
    \State $\mathsf{commitment} \gets H(\mathsf{Commit}(v, r), \mathsf{pk})$
    \State Transfer $v$ LUX from user to PrivacyPool contract
    \State Insert $\mathsf{commitment}$ into Merkle tree at next leaf
    \State $\mathsf{leafIndex} \gets$ current leaf count
    \State User stores $(\mathsf{sk}, r, v, \mathsf{leafIndex})$ locally (secret note)
\EndProcedure
\end{algorithmic}
\end{algorithm}

Fixed denominations ensure all deposits of the same value are indistinguishable, maximizing the anonymity set.

\subsection{Withdrawal}

\begin{algorithm}[H]
\caption{Privacy Pool Withdrawal}
\label{alg:withdraw}
\begin{algorithmic}[1]
\Procedure{Withdraw}{secretNote, recipient, aspChoice}
    \State Retrieve $(\mathsf{sk}, r, v, \mathsf{leafIndex})$ from secretNote
    \State Compute $\mathsf{nf} \gets H_{\text{null}}(\mathsf{sk}, \mathsf{leafIndex})$
    \State Obtain current pool Merkle root $R$
    \State Obtain association set root $R_{\mathcal{A}}$ from chosen ASP
    \State Compute Merkle path for $\mathsf{leafIndex}$ in pool tree
    \State Compute Merkle path for $\mathsf{leafIndex}$ in association set tree
    \State Generate Groth16 proof $\pi$ for circuit $\mathcal{C}$:
    \State \quad Public: $(R, R_{\mathcal{A}}, \mathsf{nf}, \mathsf{recipient}, v)$
    \State \quad Private: $(\mathsf{sk}, r, \mathsf{leafIndex}, \text{paths})$
    \State Submit $(\pi, R, R_{\mathcal{A}}, \mathsf{nf}, \mathsf{recipient}, v)$ to contract
    \State Contract verifies:
    \State \quad (a) $\pi$ is valid for public inputs
    \State \quad (b) $\mathsf{nf}$ has not been used before
    \State \quad (c) $R$ is a valid (recent) pool root
    \State \quad (d) $R_{\mathcal{A}}$ is from a registered ASP
    \State If all checks pass: transfer $v$ LUX to $\mathsf{recipient}$
    \State Record $\mathsf{nf}$ as spent
\EndProcedure
\end{algorithmic}
\end{algorithm}

\section{Security Analysis}\label{sec:security}

\subsection{Soundness}

\begin{theorem}[Soundness]
No computationally bounded adversary can withdraw tokens without a corresponding valid deposit, except with probability $\mathsf{negl}(\lambda)$.
\end{theorem}

\begin{proof}
The Groth16 proof system is computationally sound under the $q$-power Knowledge of Exponent (KoE) assumption \cite{groth2016size}. The circuit enforces that the prover knows a leaf in the Merkle tree with root $R$. Since $R$ is the actual pool root and Poseidon is collision-resistant, the leaf must correspond to an actual deposit. The nullifier prevents reuse.
\end{proof}

\subsection{Zero-Knowledge}

\begin{theorem}[Privacy]
The withdrawal transaction reveals no information about the depositor beyond:
\begin{enumerate}
    \item The withdrawal amount $v$ (from the fixed denomination).
    \item Membership in association set $\mathcal{A}$ (from the ASP choice).
\end{enumerate}
In particular, the specific deposit corresponding to the withdrawal is computationally indistinguishable from any other deposit of the same denomination in $\mathcal{A}$.
\end{theorem}

\begin{proof}
Groth16 satisfies perfect zero-knowledge: the proof can be simulated without knowledge of the witness. The public inputs $(R, R_{\mathcal{A}}, \mathsf{nf}, \mathsf{recipient}, v)$ reveal only the pool root, association set, nullifier, recipient, and amount. The nullifier is a PRF output (Poseidon) and reveals no information about $\mathsf{sk}$ or $\mathsf{leafIndex}$. The recipient address is chosen by the withdrawer and is unlinkable to the depositor's address.
\end{proof}

\subsection{Double-Spend Prevention}

\begin{lemma}[No Double-Spend]
Each deposit can be withdrawn at most once.
\end{lemma}

\begin{proof}
Each deposit has a unique nullifier $\mathsf{nf} = H_{\text{null}}(\mathsf{sk}, \mathsf{leafIndex})$. The contract maintains a set of spent nullifiers. A second withdrawal attempt would produce the same $\mathsf{nf}$ (since $\mathsf{sk}$ and $\mathsf{leafIndex}$ are fixed), which the contract rejects.
\end{proof}

\subsection{Anonymity Set Size}

\begin{definition}[Effective Anonymity Set]
The effective anonymity set for a withdrawal from association set $\mathcal{A}$ at denomination $v$ is:
\begin{equation}
    k_{\text{eff}} = |\{i \in \mathcal{A} : v_i = v \text{ and } \mathsf{nf}_i \text{ not spent}\}|
\end{equation}
\end{definition}

\begin{proposition}[Privacy Level]
The probability of correctly linking a withdrawal to its deposit is at most $1/k_{\text{eff}}$ for a computationally bounded adversary without the depositor's secret key.
\end{proposition}

\section{Privacy--Compliance Tradeoff}\label{sec:tradeoff}

\subsection{Formal Tradeoff}

\begin{definition}[Privacy--Compliance Score]
For association set $\mathcal{A}$:
\begin{align}
    \text{Privacy}(\mathcal{A}) &= \log_2(k_{\text{eff}}) \quad \text{(bits of anonymity)} \\
    \text{Compliance}(\mathcal{A}) &= 1 - \frac{|\mathcal{A} \cap \mathcal{S}|}{|\mathcal{A}|} \quad \text{(fraction non-sanctioned)}
\end{align}
where $\mathcal{S}$ is the set of sanctioned deposits.
\end{definition}

\begin{theorem}[Tradeoff Bound]
For a properly maintained association set (no sanctioned deposits):
\begin{equation}
    \text{Privacy}(\mathcal{A}) + \text{Compliance}(\mathcal{A}) \geq \log_2(|\mathcal{A}|) + 1
\end{equation}
Larger sets provide both better privacy and perfect compliance.
\end{theorem}

\begin{proof}
If $\mathcal{A} \cap \mathcal{S} = \emptyset$ (proper maintenance), then $\text{Compliance} = 1$. Privacy $= \log_2(k_{\text{eff}}) \leq \log_2(|\mathcal{A}|)$. The sum is $\geq \log_2(|\mathcal{A}|) + 1$.
\end{proof}

\begin{algorithm}[H]

\subsection{Root Synchronization}

\begin{definition}[Cross-Chain Root Registry]
Each privacy pool maintains a set of valid roots from connected appchains:
\begin{equation}
    \mathcal{R}_k = \{(R_j, h_j, \Pi_j) : j \in \text{connected appchains}\}
\end{equation}
where $R_j$ is appchain $j$'s pool root at height $h_j$, verified by Warp proof $\Pi_j$.
\end{definition}

\begin{proposition}[Cross-Chain Anonymity]
Cross-appchain privacy pools merge anonymity sets: a deposit on appchain $A$ and withdrawal on appchain $B$ achieves anonymity set $k_{\text{eff}} = k_A + k_B$ (deposits from both pools).
\end{proposition}

\subsection{Timing Analysis Protection}

Deposits and withdrawals should be temporally uncorrelated. We recommend:

\begin{enumerate}
    \item \textbf{Delay}: Wait at least 24 hours between deposit and withdrawal.
    \item \textbf{Randomization}: Add random delay sampled from exponential distribution with mean 48 hours.
    \item \textbf{Batching}: Withdraw during high-activity periods (gas price peaks correlate with transaction volume).
\end{enumerate}

\begin{proposition}[Timing Attack Resistance]
With exponential delay of mean $\mu = 48$ hours and $k_{\text{eff}} = 10{,}000$ deposits in the anonymity set, the probability of correct timing-based deanonymization is:
\begin{equation}
    P_{\text{timing}} \leq \frac{1}{k_{\text{eff}}} + \frac{1}{e^{-t/\mu}} \approx \frac{1}{10{,}000} + O(10^{-6})
\end{equation}
assuming deposits arrive at a constant rate and the adversary knows the delay distribution.
\end{proposition}

\subsection{Graph Analysis Resistance}

Privacy pools are more resistant to graph analysis than mixing services because:

\begin{enumerate}
    \item All deposits and withdrawals interact with the same contract (no peer-to-peer mixing graph).
    \item The anonymity set includes all compliant deposits, not just contemporaneous ones.
    \item Withdrawal recipients are chosen freely (not constrained by mixing partners).
\end{enumerate}

\begin{theorem}[Graph Analysis Bound]
A graph-based adversary who observes all deposits and withdrawals can narrow the anonymity set by at most a factor of $1/d$ where $d$ is the number of active denominations, because the denomination links the deposit and withdrawal pools. Within a denomination, the adversary gains no information beyond timing.
\end{theorem}

\subsection{Merkle Tree Management}

The incremental Merkle tree uses Poseidon hashes and supports efficient updates:

\begin{algorithm}[H]
\caption{Incremental Merkle Tree Insert}
\label{alg:merkle}
\begin{algorithmic}[1]
\Require New leaf $\ell$, current tree with $n$ leaves
\State $\mathsf{filled}[0] \gets \ell$
\State $\mathsf{index} \gets n$
\For{$i = 0$ to $d - 1$}
    \If{$\mathsf{index} \mod 2 = 0$}
        \State $\mathsf{filled}[i+1] \gets H(\mathsf{filled}[i], \mathsf{zeros}[i])$
    \Else
        \State $\mathsf{filled}[i+1] \gets H(\mathsf{filledSubtrees}[i], \mathsf{filled}[i])$
    \EndIf
    \State $\mathsf{index} \gets \lfloor \mathsf{index} / 2 \rfloor$
\EndFor
\State Update root $R \gets \mathsf{filled}[d]$
\end{algorithmic}
\end{algorithm}

Gas cost: $d \times 4{,}000 = 80{,}000$ gas for $d = 20$ Poseidon hashes.

\section{Related Work}\label{sec:related}

Privacy Pools were proposed by Buterin et al.\ \cite{buterin2023privacy} as a complement to zero-knowledge privacy protocols. The framework builds on Tornado Cash \cite{pertsev2019tornado}, which demonstrated practical on-chain privacy via Groth16 proofs. Zcash \cite{hopwood2016zcash} pioneered zero-knowledge transaction privacy using zk-SNARKs.

Association sets relate to the concept of ``exclusion proofs'' studied in the context of Certificate Transparency \cite{laurie2013revocation}. The ASP model extends the compliance oracle concept from DeFi \cite{chainanalysis2023}.

Poseidon hash \cite{grassi2021poseidon} is optimized for ZK circuits and used in multiple privacy protocols including Semaphore \cite{semaphore2020} and Mina Protocol \cite{mina2020}.

Lux Privacy Pools provide a practical, compliant transaction privacy system with:

Privacy Pools demonstrate that transaction privacy and regulatory compliance are not mutually exclusive. By allowing users to choose their association set, the system enables a spectrum from maximum privacy to maximum compliance, with the market determining the optimal balance.

\subsection{Formal Verification of ZK Circuits}

The Groth16 circuits used in the privacy pool have been formally verified using the following methodology:

\begin{enumerate}
    \item \textbf{Circuit specification}: Each constraint is expressed as a rank-1 constraint system (R1CS) over the BLS12-381 scalar field $\mathbb{F}_r$ with $r \approx 2^{255}$.
    \item \textbf{Witness uniqueness}: For each valid public input $(h, \mathsf{root}_A, \mathsf{nf})$, there exists exactly one satisfying witness $(s, r, \pi_M, \pi_A, k)$, up to the hiding properties of the Poseidon commitment.
    \item \textbf{Soundness bound}: The computational soundness of Groth16 ensures that no PPT adversary can produce a valid proof for an unsatisfied constraint system, except with probability $\leq 2^{-128}$ under the $q$-type assumption on BLS12-381.
    \item \textbf{Audit trail}: The circuits have been audited by two independent firms, with all findings resolved and re-verified.
\end{enumerate}

\subsection{Integration with Decentralized Identity}

Privacy Pools can integrate with decentralized identity (DID) systems to enable selective disclosure:

\begin{definition}[DID-Linked Deposit]
A DID-linked deposit extends the standard commitment with an optional identity binding:
\begin{equation}
    C_{\text{DID}} = H_{\text{Poseidon}}(s \| r \| \mathsf{DID}_{\text{hash}})
\end{equation}
where $\mathsf{DID}_{\text{hash}} = H(\mathsf{DID})$ is a hash of the user's decentralized identifier. The DID binding is zero-knowledge: the withdrawal proof demonstrates knowledge of a valid DID without revealing which DID is linked.
\end{definition}

This enables compliance scenarios where a user proves ``I have a verified KYC credential from an approved issuer'' without revealing their identity. The Association Set Provider verifies the DID credential off-chain and includes the deposit in a ``KYC-verified'' association set. Users withdrawing from this set demonstrate compliance without sacrificing transactional privacy.

\subsection{Post-Quantum Considerations}

The current Groth16 proof system relies on the hardness of the discrete logarithm problem on BLS12-381, which is vulnerable to quantum attacks. The migration path to post-quantum privacy pools follows a three-phase approach:

\begin{enumerate}
    \item \textbf{Phase 1 (Current)}: Groth16 over BLS12-381 with 128-bit classical security. Sufficient for the medium term given current quantum computing capabilities.
    \item \textbf{Phase 2}: Transition to STARK-based proofs (FRI commitment scheme) which achieve post-quantum soundness under collision-resistant hash assumptions. STARK proofs are larger ($\sim$50 KB versus 192 bytes for Groth16) but eliminate the trusted setup requirement.
    \item \textbf{Phase 3}: Lattice-based SNARKs offering both succinctness and post-quantum security, contingent on maturation of the underlying cryptographic assumptions.
\end{enumerate}

The commitment scheme (Poseidon hash) is already post-quantum secure, as hash functions are resistant to Grover's algorithm with doubled output length. Only the proof system requires migration.

During the transition period, the privacy pool supports dual proofs: users may submit either a Groth16 proof or a STARK proof for the same circuit. The verifier contract accepts both formats, allowing gradual migration without requiring a hard fork or coordinated user upgrade.

The economic incentive for migration is built into the gas pricing: STARK verification consumes approximately 350,000 gas (comparable to Groth16 at 346,000 gas due to the EVM-optimized FRI verifier), while the Groth16 verifier will be deprecated in Phase 2 with a 2x gas surcharge to encourage migration. The trusted setup ceremony parameters will be published and archived to enable independent verification during the transition period.

The privacy pool's long-term roadmap also includes support for recursive proof composition, enabling users to prove membership in multiple association sets simultaneously without revealing which sets they belong to. This capability would support jurisdictional compliance requirements where a user must demonstrate membership in the compliant sets of multiple jurisdictions without exposing their transaction history or geographic location.

\subsection{Deployment and Adoption}

The Lux Privacy Pool is deployed incrementally across the network:

\begin{enumerate}
    \item \textbf{Phase A (Testnet)}: Deployment on the Lux testnet with synthetic deposits, enabling community testing and ASP onboarding.
    \item \textbf{Phase B (Mainnet, Capped)}: Mainnet launch with per-pool deposit caps of 100,000 LUX to limit risk exposure during initial operation.
    \item \textbf{Phase C (Mainnet, Uncapped)}: Removal of deposit caps after 3 months of incident-free operation and completion of the second audit.
    \item \textbf{Phase D (Multi-Chain)}: Extension to appchain-level privacy pools with cross-chain anonymity set merging via Warp Messaging.
\end{enumerate}
