\begin{abstract}
ZAP is the canonical zero-copy wire protocol in the Lux substrate
(\texttt{luxfi/zap}), specced as ZAP-PQ-v1 with X25519$+$ML-KEM-768
hybrid handshake and ML-DSA-65 identity~\cite{zappqspec}. Today ZAP is
shipped end-to-end across (a)~Lux consensus and chain VMs
(\texttt{node/vms/proposervm}, \texttt{node/vms/evm},
\texttt{node/vms/platformvm/warp}, \texttt{chains/*/wire}), (b)~the
Hanzo control plane (\texttt{hanzo/kms},
\texttt{hanzo/datastore/cmd/zap-bridge}, \texttt{hanzo/gateway},
\texttt{hanzo/iam}, \texttt{hanzo/base}, and the TypeScript encoder
\texttt{hanzo/zap-es}), and (c)~a regulated exchange partner's ATS/BD/TA stack
(\texttt{liquidity/ats}, \texttt{liquidity/bd}, and the Rust port at
\texttt{liquidity/operator/src/zapclient.rs}). It is \emph{not} yet
shipped on three high-frequency AI surfaces: the Hanzo agent
control-plane (JSON-RPC + HTTP + gRPC), the MCP server (JSON-RPC over
stdio), or the Jin multimodal model server (JSON manifests + pickle/pt
tensor blobs); these three are the largest open migration delta in the
workspace. Independent benchmarks against MCP JSON-RPC report
$17\times$ serialisation speedup, $345\times$ parse speedup, $91.2\%$
memory-allocation reduction and $96.7\%$ allocation-count
reduction~\cite{zapreadme}; LP-023 measured $7.50\times$ Parse geomean
on \texttt{vms/platformvm/txs/zap\_native} relative to
\texttt{linearcodec}~\cite{lp023zapnative}. This paper inventories the
state of ZAP coverage across the three stacks
($\sim$$15$ Lux services, $\sim$$10$ Hanzo services,
$\sim$$8$ regulated-partner services), classifies each surface in a 5-tier
model, and proposes a phased rollout that closes the open delta
without introducing backwards-compat shims. Projected stack-wide
end-to-end speedup on the AI/ML/blockchain hot path is
$\bm{7.4}$--$\bm{8.6\times}$ with a $\bm{24\times}$ allocation
reduction, compounding LP-023 against the ZAP-vs-JSON-RPC ratio.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The Hanzo/Lux/partner workspace runs three nominally distinct
products~--- an AI platform (Hanzo), a blockchain platform (Lux), and
a US-regulated securities ATS$/$BD$/$TA (a regulated exchange partner)~--- on a shared
substrate. Every inter-process call in that substrate has historically
chosen a wire format independently: \texttt{linearcodec} on the chain,
JSON-RPC across the agent/MCP layer, \texttt{protobuf} for some gRPC
shims, vendor JSON over HTTP at the external boundary. The resulting
heterogeneity has two costs:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Performance.} Every wire boundary pays an encode and a
    decode tax. JSON-RPC parse on a $20$-tool MCP orchestrator round
    is measured at $109{,}175$~ns/op with $54{,}292$~B and $1{,}060$
    allocations~\cite{zapreadme}. At the fleet-wide call rate this is
    a dominant component of CPU and GC pressure.
  \item \textbf{Composability.} Heterogeneous wires defeat
    re-composition: a service speaking JSON cannot be wrapped by a
    service expecting protobuf without an adapter, and adapters
    accumulate at every layer boundary.
\end{enumerate}

ZAP is the workspace's answer to both costs. It is a zero-copy
segment-pointer wire (single allocation per parse, fixed-stride field
access, no reflect, no schema lookup at decode), specced once and
implemented in Go (\texttt{luxfi/zap}), Rust
(\texttt{liquidity/operator/src/zapclient.rs}, verbatim wire-compatible
per its module header), and TypeScript
(\texttt{hanzo/zap-es} npm package). The handshake layer is ZAP-PQ-v1,
a Noise-style hybrid post-quantum transport replacing any TLS/Noise
layer underneath the data plane~\cite{zappqspec}.

This paper is the audit step. It answers three questions:

\begin{itemize}[leftmargin=*]
  \item Which surfaces \emph{already} run ZAP today? (Tier 5)
  \item Which surfaces should run ZAP and currently don't? (Tier 1--3)
  \item Which surfaces are out of scope because they talk to external
        parties? (Tier 4)
\end{itemize}
