\section{GPU-Native EVM Execution}

\label{sec:gpu}
%% ============================================================================

The critical path of DAG-EVM is:

\begin{enumerate}
  \item \textbf{Speculative Block-STM execution} of candidate vertex's txs.
  \item \textbf{ecrecover} for every transaction in the batch.
  \item \textbf{Conflict scan} against the frontier's bitmap union.
  \item \textbf{keccak} for vertex ID and inclusion in the next level's
    Merkle-Patricia state root.
\end{enumerate}

Through the v0.20.0 $\to$ v0.23.0 release cycle (luxcpp/evm tags
\texttt{v0.22.0}, \texttt{v0.23.0}), the GPU stage stopped being a single
ecrecover kernel and grew into a full opcode-level interpreter for both
Apple Metal and NVIDIA CUDA, sharing one host-side dispatcher. The result
is that every step above can run on the same GPU device.

\subsection{Kernel Surface}

The GPU EVM kernel is a single-source artefact in two dialects:

\begin{itemize}
  \item \texttt{lib/evm/gpu/kernel/evm\_kernel.metal} (\num{1067} SLOC,
    Metal Shading Language 3.0).
  \item \texttt{lib/evm/gpu/cuda/evm\_kernel.cu} (\num{1713} SLOC, CUDA
    C++ for sm\_80 / sm\_90).
\end{itemize}

Both implement the Cancun-era opcode set including
\texttt{KECCAK256}, the Cancun context family
(\texttt{ORIGIN}/\texttt{GASPRICE}/\texttt{BLOCKHASH}/\texttt{CHAINID}/%
\texttt{BASEFEE}/\texttt{BLOBHASH}/\texttt{BLOBBASEFEE}), \texttt{MCOPY},
\texttt{TLOAD}/\texttt{TSTORE}, and \texttt{LOG0}--\texttt{LOG4}. ABI version
3 of the kernel adds a \texttt{BlockContext} buffer plus transient-storage
and log buffers (Metal binds them at indices 8--12). Account-state opcodes
(\texttt{BALANCE}, \texttt{EXTCODESIZE}, \ldots) return safe defaults
inside the kernel; live host data is provided through the bridge described
in \S\ref{sec:gpu:bridge}.

\subsection{Precompile Dispatch}

The precompile dispatcher routes addresses \texttt{0x01}--\texttt{0x11}
through GPU code paths where it is profitable. \texttt{ECRECOVER}
(\texttt{0x01}) executes on Metal and CUDA via
\texttt{secp256k1\_recover.cu}; the BLS12-381 (\texttt{0x0b}--\texttt{0x11})
EIP-2537 family is wired through the same dispatcher. The standalone unit
target \texttt{evm-precompile-test} reports 19 precompile groups passing
on the M1 Max reference hardware; the run is guarded by
\texttt{available\_backends()} so a host without a Metal device falls back
to CPU silently.

\subsection{EVMC Host Bridge for CALL/CREATE}
\label{sec:gpu:bridge}

The headline limitation of a pure-GPU EVM is that the kernel cannot make
a runtime callback into an EVMC \texttt{Host} for nested
\texttt{CALL}/\texttt{CREATE} frames; GPUs do not call back to CPU memory
mid-warp. The v0.22.0 host bridge
(\texttt{lib/evm/gpu/host/evmc\_bridge.cpp}) sidesteps this by performing a
static analysis on the entrypoint bytecode: it walks the basic-block graph,
identifies every \texttt{CALL}/\texttt{CREATE} target whose address is a
constant immediate, pre-resolves the destination code from the supplied
\texttt{evmc::Host}, and packs the entire reachable code closure into a
single GPU-side \emph{code dictionary}. Dynamic-target calls
(\texttt{CALL} where the address is computed at runtime) are rejected and
the transaction falls back to evmone on CPU.

The accept/reject decisions and depth enforcement are exercised by
\texttt{test/unittests/host\_bridge\_test.cpp}, with the seven scenarios
listed in Table~\ref{tab:hostbridge}. The bridge enforces a maximum frame
depth of 4; deeper chains route to CPU.

\begin{table}[h]
\centering
\small
\begin{tabular}{ll}
\toprule
\textbf{Scenario} & \textbf{Outcome} \\
\midrule
Pure leaf (no CALL/CREATE)            & GPU accept \\
Static \texttt{CALL} with const target & GPU accept (pre-resolved) \\
Dynamic \texttt{CALL}                  & CPU fallback \\
Deterministic \texttt{CREATE}          & GPU accept (deterministic addr) \\
4-deep static \texttt{CALL} chain      & GPU accept \\
9-deep static \texttt{CALL} chain      & CPU fallback (depth $>$ MAX) \\

\subsection{Unified Pipeline}

A single Metal device drives EVM execution, consensus state hashing
(\texttt{lib/evm/gpu/gpu\_state\_hasher.hpp}), and post-quantum signature
verification (BLS12-381 + ML-DSA-65 hosted by
\texttt{lib/evm/gpu/metal/bls\_host.mm}). The pipelined run measured at
v0.22.0 on M1 Max reports a $1.07\times$ speedup vs serial (consensus +
EVM + sig-verify) at 19 blocks/s sustained over 1000 blocks --- the
modest factor reflects the fact that each stage already saturates a
different GPU resource (compute for EVM, memory bandwidth for keccak
state hashing, BLS scalar-mult for sig-verify), so pipelining recovers
only the overlap. Source: \texttt{lib/evm/gpu/test\_unified\_pipeline.cpp}.

\subsection{Empirical Speedup, M1 Max}
\label{sec:gpu:speedup}

Two regimes need separate accounting: (a) the original
ecrecover/keccak-dominated bottleneck that motivated the GPU port at
v0.20.0, and (b) the bytecode-level kernel that came online at v0.22.0.
Table~\ref{tab:gpu-cancun} shows the ecrecover/keccak path is essentially
solved (the original $32\times$ ecrecover speedup carries over) and that
the bytecode kernel itself is faster than evmone on per-opcode microkernels
once the batch is large enough to amortise GPU dispatch.

GPU is auto-detected at runtime: if the dispatcher's
\texttt{available\_backends()} returns a non-CPU backend, the bytecode is
routed through the GPU host launcher (\texttt{evm\_kernel\_host.mm} on
Apple, \texttt{cuda/evm\_kernel\_host.cpp} on NVIDIA). When no GPU is
present, both CPU paths (\texttt{CPU\_Sequential} and
\texttt{CPU\_Parallel} via Block-STM) run unchanged. There is no user
flag.

\subsection{Limitations}

\begin{itemize}
  \item \emph{Dynamic CALL targets fall back to CPU.} The host-bridge
    static analysis only resolves constant-immediate targets. Solidity
    code that loads a callee address from storage at runtime is not yet
    GPU-eligible. Path: extend the dictionary to include the closure
    of all addresses ever stored in dispatcher slots, with re-staging
    on dictionary miss. Not yet implemented.
  \item \emph{\texttt{SELFDESTRUCT} is rejected.} The kernel returns
    \texttt{CallNotSupported} on \texttt{0xFF}; the dispatcher falls back
    to CPU. Acceptable today because Cancun deprecates the opcode for
    new accounts.
  \item \emph{Account-state opcodes return defaults inside the kernel.}
    \texttt{BALANCE}, \texttt{EXTCODESIZE}, \texttt{EXTCODEHASH},
    \texttt{EXTCODECOPY}, \texttt{SELFBALANCE} read from a host-supplied
    snapshot dictionary; addresses missing from the dictionary surface
    as zero. The host bridge populates the dictionary for every address
    it has pre-resolved; addresses outside that closure read zero. The
    parity test corpus catches this with the \texttt{state\_*} vectors.
  \item \emph{$N \le 2048$ batches lose to CPU-Parallel.} GPU dispatch
    cost (host $\to$ device buffer staging + threadgroup launch) is in the
    \SI{6}{\milli\second} range on M1 Max for cold buffers, dropping to
    $\sim$\SI{4}{\milli\second} once buffer cache is warm. CPU-Parallel
    Block-STM clears the same workload in
    $\sim$\SI{0.1}{\milli\second}--\SI{4}{\milli\second}. The crossover
    moves into the kernel's favour at $N \ge 4096$ (workload-dependent),
    or when the workload contains ecrecover/keccak which still dominate
    on CPU.
\end{itemize}
