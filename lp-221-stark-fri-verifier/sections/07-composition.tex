\section{Composition With Sibling LPs}
\label{sec:composition}

\subsection{LP-218 P3Q at slot \texttt{0x012205}}

LP-218~\cite{lp218} defines \texttt{0x012205} as a single precompile
that takes a leading kind byte ($0x01$ Pulsar, $0x02$ Corona, $0x03$
Magnetar) and verifies a PQ \textbf{threshold signature}. LP-220
\cite{lp220} extends LP-218 with the Corona and Magnetar kind
specifications on the same slot. LP-221 (this LP) defines
\texttt{0x012220} as a single precompile that verifies a STARK
\textbf{proof}. The two are composed at the rollup layer:

\begin{itemize}[leftmargin=2em,nosep]
\item LP-218 \texttt{RollupBatchTx} (schema \texttt{0xE8}) carries
  both a \texttt{pulsar\_sig} field and a \texttt{ZKProofOff}
  field.
\item A \textbf{ZK-rollup} variant carries both: the Pulsar
  signature authenticates the sequencer's commit, and the STARK
  proof authenticates correct execution of the batch under the
  rollup-VM's transition relation.
\item An \textbf{optimistic-rollup} variant carries only the
  Pulsar signature; \texttt{ZKProofOff = 0} and the integrity
  model is fraud-proof challenges (LP-218 schema \texttt{0xE9}
  \texttt{RollupChallengeTx}).
\end{itemize}

Z-Chain block validation under the ZK-rollup variant calls
\textbf{both precompiles}: \texttt{0x012205} for the signature,
\texttt{0x012220} for the proof. Both must accept. No nested call.
Gas budget is the sum: Pulsar verify $\sim$\num{50000} $+$ STARK
verify $\sim$\num{500000} $\approx$ \num{550000} gas per
ZK-rollup batch under typical parameters.

\subsubsection{Sample ZK-rollup validator (Solidity)}

\begin{lstlisting}[language={}]
function validateZKBatch(
    bytes32 prevRoot,
    bytes32 newRoot,
    bytes32 batchHash,
    bytes calldata pulsarSig,
    bytes calldata groupPk,
    bytes calldata starkProof,
    bytes calldata pubInputs
) external returns (bool) {
    bytes32 h = sha256(abi.encodePacked(prevRoot, newRoot, batchHash));

    // Signature leg: WHO authored this batch
    if (!P3Q.verify(0x01, pulsarSig, h, groupPk)) return false;

    // Proof leg: WHAT was executed
    if (!STARKFRI.verify(VersionV1, starkProof, pubInputs)) return false;

    return true;
}
\end{lstlisting}

Two precompiles, two slots, two checks. The Solidity caller does
not need to know that they live at different slots; the import
shims (\texttt{P3Q.verify} at \texttt{0x012205}, \texttt{STARKFRI.verify}
at \texttt{0x012220}) hide the slot allocation behind named
function calls.

\subsection{LP-0120 PQ precompile band}

LP-0120 owns the \texttt{0x012201..0x012208} PQ-signature~/ KEM
band. LP-221 sits one nibble above at \texttt{0x012220},
\textbf{chosen so the strict-PQ STARK family can grow its own
sub-range (\texttt{0x012220..0x01222F}) without recolliding with
the PQ-signature block}. Future SNARK-family allocations
(recursive STARK, hash-based zkVM variants, etc.) land inside
\texttt{0x012220..0x01222F} per LP-300 master registry amendments.

\subsection{LP-300 master schema registry}

LP-300~\cite{lp300} is normative for the slot pin. LP-221 carries
the slot informatively. Any future amendment to LP-221's wire
format, gas schedule, or version byte must be registered in
LP-300 first.

The LP-300 row for \texttt{0x012220} is closed by this LP. Per
Section~\ref{sec:specification}~\S``Cross-reference to the
registry'', the post-LP-221 row should read:

\begin{quote}
\texttt{0x012220 -- LP-221 -- STARK-FRI -- Plonky3-fork FRI~/
cSHAKE256~/ Goldilocks STARK verifier; magic header "P3Q1"
preserved verbatim for proof-artifact stability -- Draft --
2026-06-04.}
\end{quote}

\subsection{LP-4800 and LP-4820 (related primitives)}

LP-4800 and LP-4820 are the broader strict-PQ SNARK substrate LPs
(parameter schedules, transcript bindings, and recursive-proof
extensions). LP-221 implements the EVM-callable verifier surface
for the LP-4800 baseline; recursive variants from LP-4820 will
land at separate slots inside the reserved \texttt{0x012220..0x01222F}
range with their own version bytes or dedicated LPs.

The split is deliberate: LP-221 is normative for the
on-chain ABI and gas; LP-4800 / LP-4820 are normative for the
prover-side parameter discipline. A future LP-221 amendment that
grafts a new prover parameter schedule must coordinate with the
corresponding LP-4800 amendment to keep the prover/verifier
parameter pair in lockstep.

\subsection{LP-203 GPU-native verify}

LP-203~\cite{lp203} specifies the Blackwell sm\_120 batched-verify
dispatch path. A STARK batch verify kernel for LP-221 is projected
at \texttt{lux/accel/cuda/starkfri.cu} (not yet implemented at
LP-221 publish time). The projected per-verify cost on Blackwell
sm\_120 is $\sim$\SI{50}{\micro\second} amortized across a batch
of $\sim$$64$ proofs; the gas schedule above is sized to the
CPU-class verify cost (\SIrange{5}{10}{\milli\second}), so GPU
acceleration is a node-operator latency improvement, not a gas
reduction. LP-221 does NOT claim measured GPU throughput; that
lands when the kernel ships.

The LP-203 dispatch shim (\texttt{lux/accel/c\_api.h}) will gain
\texttt{lux\_starkfri\_verify\_batch} as one of its entry points
once the kernel ships; the precompile's
\texttt{RegisterVerifier} hook accepts the GPU-backed verifier
function as a drop-in replacement for the CPU verifier, with the
hot-swap pattern preserved (atomic load on the verifier function
pointer).

\subsection{LP-217 cert profile modes}

LP-221 is orthogonal to the QuasarCert ladder (PQ-off, PQ-fast,
PQ-strict, PQ-heavy)~\cite{lp217}. The STARK verifier is invoked
inside EVM execution, not inside consensus cert formation. Cert
profile mode affects how LP-221's precompile call is
\textbf{finalized} (which signature families validate the
containing block) but does not affect the precompile's verify
cost or correctness.

\begin{table}[h]
\centering
\small
\begin{tabular}{@{}p{4.2cm}p{4.5cm}p{4cm}@{}}
\toprule
\textbf{LP-217 mode} & \textbf{Block cert leg set} & \textbf{LP-221 STARK verify} \\
\midrule
\texttt{PQ-off}    & BLS only & callable; result trusted under classical adversary \\
\texttt{PQ-fast}   & BLS + P3Q($0x01$ Pulsar) & callable; result trusted under PQ adversary \\
\texttt{PQ-strict} & BLS + P3Q($0x01$) + P3Q($0x02$ Corona) & callable; result trusted under cross-family PQ adversary \\
\texttt{PQ-heavy}  & BLS + P3Q($0x01$) + P3Q($0x02$) + P3Q($0x03$ Magnetar) & callable; result trusted under three-family-independent PQ adversary \\
\bottomrule
\end{tabular}
\caption{LP-217 cert profile mode affects block finalization (the
signature legs that validate the containing block), not the
STARK-FRI precompile's verify path. The verify path is the same
across all four modes; the cert mode determines what \emph{else}
must verify to finalize the block carrying the STARK verify call.}
\label{tab:cert-modes-starkfri}
\end{table}

\subsection{Backwards compatibility}

None. The pre-Quasar Edition Lux network (2020--2025) had no
STARK-FRI precompile and is a separate network out of scope. The
genesis state of the new final Lux network (activation
\texttt{2025-12-25T16:20:00-08:00}) ships the LP-221 ABI at slot
\texttt{0x012220} as the only ABI; no shim exists for any
pre-LP-221 STARK verifier (there was no such verifier on any
running network).
