\begin{abstract}
We present the Lux API Gateway, a high-performance infrastructure layer providing RPC and REST access to blockchain nodes. The system implements adaptive rate limiting based on client behavior and network load, consistent hashing-based load balancing across node clusters, and multi-tier caching with cache coherence for blockchain data. Our architecture handles 100,000 requests per second with P99 latency under 50ms while protecting backend nodes from overload. We introduce novel techniques for request coalescing, speculative execution, and cache invalidation triggered by block finalization events.
\end{abstract}

\section{Introduction}

Blockchain APIs serve as the primary interface between applications and the underlying network. As decentralized applications scale, API infrastructure must handle millions of requests while maintaining low latency and high availability. Key challenges include:

\begin{itemize}
    \item \textbf{Traffic Spikes}: NFT mints and DeFi events cause 100x load increases
    \item \textbf{Heterogeneous Requests}: Range from simple balance queries to complex trace calls
    \item \textbf{Data Freshness}: Balance between caching and blockchain state recency
    \item \textbf{Attack Resistance}: Protection against DoS and resource exhaustion attacks
\end{itemize}

The Lux API Gateway addresses these challenges through:

\begin{enumerate}
    \item \textbf{Adaptive Rate Limiting}: Token bucket with dynamic refill based on client history
    \item \textbf{Intelligent Load Balancing}: Consistent hashing with health-aware routing
    \item \textbf{Blockchain-Aware Caching}: Block-triggered invalidation with speculative refresh
    \item \textbf{Request Optimization}: Coalescing, batching, and connection pooling
\end{enumerate}

\section{Rate Limiting}

\subsection{Token Bucket with Adaptive Refill}

Standard token bucket with dynamic adjustment:

\begin{definition}[Adaptive Token Bucket]
For client $c$ with base rate $r_c$ and current network load $\ell$:
\[
r_{\text{effective}}(c) = r_c \cdot (1 - \ell) \cdot \text{reputation}(c)
\]
where $\ell \in [0, 1]$ is system load factor.
\end{definition}

\begin{algorithm}
\caption{Adaptive Rate Limiter}
\begin{algorithmic}[1]
\Procedure{CheckRateLimit}{$client$, $cost$}
    \State $bucket \gets \text{GetBucket}(client)$
    \State $now \gets \text{CurrentTime}()$
    \State $elapsed \gets now - bucket.\text{lastUpdate}$
    \State $refill \gets elapsed \cdot \text{GetEffectiveRate}(client)$
    \State $bucket.\text{tokens} \gets \min(bucket.\text{capacity}, bucket.\text{tokens} + refill)$
    \State $bucket.\text{lastUpdate} \gets now$

    \If{$bucket.\text{tokens} \geq cost$}
        \State $bucket.\text{tokens} \gets bucket.\text{tokens} - cost$
        \Return \text{ALLOW}
    \Else
        \State $\text{UpdateReputation}(client, -1)$
        \Return \text{DENY}
    \EndIf
\EndProcedure
\end{algorithmic}
\end{algorithm}

\subsection{Health-Aware Routing}

Node health is continuously monitored:

\begin{lstlisting}
Health Metrics:
  - Latency (P50, P95, P99)
  - Error rate
  - Queue depth
  - Block height (sync status)
  - CPU/Memory utilization

Health Score: weighted average
  weight_latency = 0.3
  weight_errors = 0.3
  weight_queue = 0.2
  weight_sync = 0.2
\end{lstlisting}

\begin{algorithm}
\caption{Health-Aware Node Selection}
\begin{algorithmic}[1]
\Procedure{SelectNode}{$request$}
    \State $key \gets \text{Hash}(request.\text{key})$
    \State $candidates \gets \text{GetCandidates}(key, 3)$ \Comment{3 closest nodes}
    \State $best \gets \text{nil}$
    \State $bestScore \gets 0$
    \For{$node \in candidates$}
        \If{$node.\text{health} > bestScore$}
            \State $best \gets node$
            \State $bestScore \gets node.\text{health}$
        \EndIf
    \EndFor
    \If{$bestScore < 0.5$}
        \Return $\text{AnyHealthyNode}()$ \Comment{Fallback}
    \EndIf
    \Return $best$
\EndProcedure
\end{algorithmic}
\end{algorithm}

\subsection{Block-Triggered Invalidation}

Cache invalidation on new blocks:

\begin{algorithm}
\caption{Block-Triggered Cache Invalidation}
\begin{algorithmic}[1]
\Procedure{OnNewBlock}{$block$}
    \State $\text{InvalidateLatest}()$ \Comment{All "latest" entries}
    \If{$block.\text{height} \mod 32 = 0$}
        \State $\text{PromoteFinalized}(block.\text{height} - 64)$
    \EndIf
    \For{$tx \in block.\text{transactions}$}
        \State $\text{InvalidateAffectedAccounts}(tx)$
    \EndFor
    \State $\text{SpeculativeRefresh}(\text{hotKeys})$
\EndProcedure
\end{algorithmic}
\end{algorithm}

\subsection{Request Coalescing}

Identical concurrent requests are coalesced:

\begin{lstlisting}
Coalescing Logic:
  1. Hash request to get coalesce key
  2. Check if request in-flight for same key
  3. If yes: subscribe to result channel
  4. If no: execute and broadcast result

Benefits:
  - Reduces backend load during spikes
  - Improves latency for duplicate requests
  - Natural protection against thundering herd
\end{lstlisting}

\section{Request Optimization}

\subsection{Batch Request Processing}

JSON-RPC batch requests are parallelized:

\begin{algorithm}
\caption{Parallel Batch Processing}
\begin{algorithmic}[1]
\Procedure{ProcessBatch}{$requests$}
    \State $groups \gets \text{GroupByNode}(requests)$
    \State $results \gets \text{make}(\text{map})$
    \State $wg \gets \text{WaitGroup}()$
    \For{$(node, reqs) \in groups$}
        \State $wg.\text{Add}(1)$
        \State \textbf{go} \Call{ProcessGroup}{$node$, $reqs$, $results$, $wg$}
    \EndFor
    \State $wg.\text{Wait}()$
    \Return $\text{ReorderResults}(requests, results)$
\EndProcedure
\end{algorithmic}
\end{algorithm}

\section{Related Work}

\textbf{Infura}~\cite{infura}: Pioneering blockchain API provider. Centralized architecture limits scalability and introduces single point of failure.

\textbf{Alchemy}~\cite{alchemy}: Enhanced APIs with custom indexing. Focus on developer experience over raw performance.

\textbf{The Graph}~\cite{thegraph}: Decentralized indexing protocol. Complementary for complex queries but higher latency.

\textbf{Pocket Network}~\cite{pocket}: Decentralized RPC network. Trading latency for decentralization.

\section{Conclusion}

The Lux API Gateway provides high-performance, resilient access to blockchain nodes. Key contributions:

\begin{itemize}
    \item Adaptive rate limiting with reputation scoring
    \item Health-aware load balancing with circuit breakers
    \item Multi-tier caching with block-triggered invalidation
    \item 100,000 RPS with sub-50ms P99 latency
\end{itemize}

Future work includes geographic distribution for lower latency, GraphQL support for flexible queries, and integration with decentralized RPC networks.
